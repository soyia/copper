# Copper 0.4.0-rc.11 内部备份链恢复验收候选

`INTERNAL_REHEARSAL_ONLY`。rc.10 已完成真实三镜像构建、M4 安全扫描和离线介质封装，但全量/增量恢复链的实际旁路 stage 在数据库应用前失败：公开 payload checksum 中的 `./config/runtime-allowlist.json` 被读取器拒绝。rc.10 冻结清单、镜像、备份原件、失败日志和经营基线全部保留，不能把该轮记为恢复通过。

## 功能变化

修复 checksum 读取器与正式 `backup create` 产物的路径表示兼容性，仅对校验清单中的正常 `./` 前缀执行受控规范化。规范化后的重复项、绝对路径和目录穿越仍须拒绝；附件和其他 payload 路径的全局严格校验保持原样。不修改旧备份、不更改加密格式或停写边界，也不通过重写归档绕过读取器。

本候选必须使用正式 amd64 工厂重新构建三张镜像，可使用正常构建缓存，但以新构建实际产生并重新导入的摘要和 provenance 为准。Backend/Web 业务源码未增加功能；新产品版本、Deploy 运行时和实际镜像证据须重新冻结，并运行本候选的 M4、离线封装和引导介质验证。rc.10 的原始构建与扫描记录不得改写成 rc.11 的新结果。

离线 Docker 清单与 rc.10 已核验的五个 DEB 逐字节一致，仍使用 Docker Engine 29.9.2 与 Compose Plugin 5.6.1。实际原件、包摘要和版权材料按同一精确身份复验。其他许可/NOTICE 原件只在身份、版本和字节确实相同时复用事实，最终总材料仍须绑定本轮真实六角色 SBOM 与新三镜像；四个源侧原件/署名缺口和外部法律确认保留待复核，不制造权利人或正式 M6 通过。

## 数据库影响

本次读取器修复不新增或修改 Flyway。目标 schema、迁移清单及摘要由实际 Backend 冻结输入生成。库存、应收应付、资金、附件与核心外键口径须在新安装及恢复后的真实数据链中复验。

## 已知问题与验收

当前为候选准备说明，不是构建、扫描、安装或恢复通过回执。实际验收仍使用本会话授权的 Ubuntu 24.04 x86_64 主机，主机不映射 Backend 8191 或 MySQL 3306。

在同一最终介质上重新完成真实安装、经营与两份附件、全量和增量加密备份、独立解密、旁路 stage/switch、继续经营与 down/up；随后必须创建新的 full，独立解密并重新 stage 验证恢复后新增的经营数据。错误路径拒绝与旧备份原字节保留均须取证。浏览器/手机及外部法律、会计、独立安装者、客户见证等沿用产品负责人明确的内部非阻断延期，不伪称第三方验收或签字。

## 升级步骤

仅作为 `freshInstallOnly:true`、直接升级来源为空的新装候选；不承诺 rc.10 或任何未实测版本可直接升级。读取 checksum 的兼容修复也不等于跨版本恢复已通过。

## 停机与回退

正式停写与切换后保留原站 rollback 槽，不以旧镜像写入或逆向 SQL 回滚 schema。本轮不创建公开 Release、不打发布标签、不部署客户生产环境。
