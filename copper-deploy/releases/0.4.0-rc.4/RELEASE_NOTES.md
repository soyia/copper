# Copper 0.4.0-rc.4 M7-04 内部连续经营候选说明

> `INTERNAL_REHEARSAL_ONLY`：本候选仅用于 M7-04 升级、备份、恢复、换机、导出和断网连续经营演练，不是 Git tag、GitHub Release 或客户交付物。

## 功能变化

- 把 M7-03 已验证的业务站点纳入受支持升级状态机，升级前强制生成新的加密一致性整站备份。
- 使用保留旁路完成目标镜像、Flyway、业务总量、附件、引用完整性和三层健康验证；未经人工确认不切换正式站点。
- 补齐 M7-04 的升级失败、切换失败、完整回滚、独立换机恢复、完整导出和断网经营证据口径。
- 本候选优先验证 Deploy 与运维生命周期；业务 schema 保持 7，不在同一次演练中混入新的业务数据迁移风险。

## 数据库影响

- 目标 schema 仍为 7，迁移集合严格绑定 V1 至 V7；本候选不新增、删除或重写任何迁移。
- 唯一直接来源是 `0.4.0-rc.3 / schema 7`。其他版本或 schema 未列入矩阵即拒绝直接升级。
- 即使 schema 未变化，仍必须核对 Flyway 历史、经营财务总量、附件摘要和引用完整性，禁止只换镜像后宣称升级成功。

## 已知问题

- 本候选是内部演练，不构成正式发布、源码授权、客户双人交接或 Certified 结论。
- 单台 2 vCPU / 4 GiB 主机不适合长期同时运行正式站与完整旁路站；旁路只在维护窗口内受控运行，换机恢复使用独立环境。
- 同机本地备份不构成整机灾难保护；M7-04 必须另行验证客户持钥的离线副本和独立恢复环境。
- GitHub 平台历史引用、第三方权利、外部专业复核和 M5 实体延期项继续记录为 `FORMAL_RELEASE_BLOCKED`，但不阻断本次内部演练。

## 升级步骤

1. 记录来源站版本、schema、三项镜像 ID、经营财务基线、附件摘要、磁盘与资源余量。
2. 将绑定本候选的离线交付目录暂存为 READY，执行 `upgrade preflight` 和 `upgrade prepare`；任何门槛失败都不修改当前站点。
3. 用客户临时恢复身份在隔离旁路执行 `upgrade migrate`，验证目标 schema、业务总量、附件和三层健康。
4. 先注入一次失败并验证当前站继续健康，再重新准备成功样本；只有人工输入完整确认文本后才切换。
5. 切换后复核版本、数据、审计和监控；随后执行一次正式工具回滚，再完成第二次升级并保留最终目标版本。

## 停机与回退

- 预计停机只发生在最终原子切换和三层复核窗口；准备、备份和隔离迁移期间来源站恢复后继续服务。
- 切换前失败必须保持来源站运行；切换失败必须自动验证来源站或保留现场并停止 Web，禁止带病放行。
- 切换后回退只允许使用保留旁路或已离线验证的整站备份；禁止逆向 SQL、覆盖目录或手工替换旧镜像。
- 旧数据、旧配置、升级专属备份和 root-only 审计证据在人工确认完成前不得删除。
