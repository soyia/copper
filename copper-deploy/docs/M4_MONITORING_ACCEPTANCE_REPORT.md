# M4-04 应用、数据库、磁盘、备份、证书与时间监控验收报告

验收日期：2026-07-15（Asia/Shanghai）

## 结论

M4-04 已通过代码合同、全仓回归和 Ubuntu 24.04 x86_64 真实主机验收。客户现在可以仅依靠自有服务器上的 `copperctl monitor`，独立查看存活、就绪、可写、可恢复、容量、备份、恢复密钥实证、HTTPS 证书和系统时间状态；完全断开公共网络时仍可检查并读取 root-only 本地状态。

验收覆盖正常、预警、严重/阻断、通知失败和恢复，不查询业务明细、不计算分页业务汇总、不保存秘密。M4-04 只证明监控、状态和通知合同；数据库真实中断、磁盘真实耗尽、证书真实过期和异常断电后的经营财务不变量复核属于 M4-06，不在本项冒充完成。

## 实现范围

- 新增 `copperctl monitor check|status|history|schedule`，`copperctl` 版本提升到 `0.8.0-m4`。
- 区分容器存活、Web/Backend/数据库就绪、数据库与文件区可写、备份与客户恢复密钥可恢复四层状态。
- 数据库使用业务账户执行无持久副作用的临时表写入探测，同时记录 MySQL 和 Flyway 版本、只读状态。
- 记录系统盘、数据盘和数据库、附件、导出、备份、日志五类占用；至少 6 小时有效历史后计算增长速度和 7/30 天容量风险。
- 读取 root-only 备份任务和密钥登记状态，显示最后成功、连续失败、目标、完整包校验、双人交接与离线恢复回执，不显示公钥原文和备份文件名。
- 本地读取 Caddy、公网 IP 或客户指定的公开证书链，检查剩余有效期；不读取证书私钥，不依赖公网探测。
- 同时显示宿主机时区、应用时区、NTP 同步和 Chrony/systemd-timesyncd 偏差。
- 状态原子写入 `${COPPER_VAR_DIR}/monitor/status.json`，历史写入有界 `history.jsonl`；目录 `0700`、文件 `0600`，权限过宽或符号链接直接拒绝。
- 默认告警完全本地；可选客户自有 HTTPS Webhook 使用 HMAC-SHA256，只发送站点指纹、等级、时间和固定动作码。通知失败保留本地健康事实和 `DELIVERY_FAILED` 证据。
- 正式安装自动启用每 5 分钟 systemd timer；卸载时移除 timer 但保留监控历史。

## 固定状态与阈值

| 信号 | 预警 | 严重 | 阻断 |
| --- | --- | --- | --- |
| 磁盘 | `<20%` 或 `<5 GiB` | `<10%` 或 `<2 GiB` | `<5%` 或 `<1 GiB` |
| 增长预测 | 30 天内进入严重区 | 7 天内进入严重区 | 由当前磁盘阻断门槛决定 |
| 最近成功备份 | 超过 30 小时 | 超过 48 小时或连续失败至少 2 次 | 没有可验证成功备份 |
| 恢复密钥 | — | — | 活动公钥、双人交接或离线恢复回执不完整 |
| 域名证书 | 剩余 30 天 | 剩余 7 天 | 已过期或 Copper 管理模式缺少证书 |
| 公网 IP 证书 | 剩余 2 天 | 剩余 12 小时 | 已过期或缺少证书 |
| 系统时间 | 偏差至少 1 秒 | NTP 未同步或偏差至少 5 秒 | 偏差至少 60 秒 |

每个非正常信号均包含等级、发生时间、原因、下一步和固定动作码。正常、预警退出码为 0；严重、阻断退出码为 1；配置或状态权限不安全为 3。

## 实际场景与结果

### 1. 正常状态

- MySQL、Backend、Web 均为 `running/healthy`，Web 存活和 Backend readiness 通过。
- MySQL `8.4.10`、Flyway `5`，业务账户临时表写入成功，业务文件区写入/清理成功。
- 四层均为 `NORMAL`，总体 `NORMAL`。
- 数据盘 50,884,108,288 字节，剩余 40,167,976,960 字节（78.9%）。
- 实际采集数据库 232,227,546 字节、附件 0、导出 0、备份 52,218、应用日志 7,634 字节。
- 真实一致性加密整站备份通过内外层校验，最近成功目标为 `local`、连续失败 0。
- 测试客户恢复密钥完成双人登记和真实离线解密回执，“可恢复”为正常；测试私钥未进入受控服务器目录并在验收后销毁。
- HTTPS 公开测试证书的域名匹配与剩余 90 天均通过；NTP 已同步，Chrony 偏差约 0.021246 毫秒。宿主机时区为 `Etc/UTC`，应用时区为 `Asia/Shanghai`，两者分别明确展示。

### 2. 完全断网检查

在 Linux 独立网络命名空间中执行完整 `monitor check`，阻断该进程的公共网络访问。Docker Unix socket、本地容器回环探测、本地证书、备份状态和 Chrony 仍可读取，四层和总体保持 `NORMAL`。这证明核心监控不依赖 Copper、GHCR、公共 DNS、许可证心跳或第三方 SaaS。

### 3. 容量预警

仅在 `COPPER_TEST_MODE=1` 使用测试故障注入把可用空间观测值设为 8 GiB；没有填满或删除真实磁盘数据。结果为总体 `WARNING`、可写层 `WARNING`，`storage.dataFilesystem=WARNING`，其他三层正常，本地通知结果 `LOCAL_ONLY`。

### 4. 数据库阻断

仅在测试模式注入数据库不可用观测；没有停止真实 MySQL 或破坏测试数据。结果为总体 `BLOCKED`，就绪和可写层均 `BLOCKED`，明确产生 `database.availability`、`database.writable` 两个阻断信号，命令退出 1。真实数据库中断和事务/经营不变量检查留给 M4-06。

### 5. 通知失败

切换到隔离回环的不可达 Webhook，并注入一次通知投递失败。健康事实仍先写入本地状态，总体保持可解释的 `WARNING`；通知记录为 `FAILED / DELIVERY_FAILED`，同时产生 `notification.delivery=WARNING`。JSON 不含 URL、HMAC、证书私钥、备份文件名或业务数据。

### 6. 恢复和停机后可查

移除故障注入并恢复本地通知后，四层与总体重新变为 `NORMAL`，恢复事件记录为 `LOCAL_ONLY`。随后删除隔离容器和网络，再执行只读 `monitor status --json`，仍能返回最后正常状态；该命令不要求 Docker 或公网可用。

## 安全门槛实证

首次实机尝试在管理员一次性凭据尚未完成改密时创建整站备份，备份脚本正确拒绝并记录本地失败，没有发布备份。验收脚本因此补齐真实登录、强制改密和凭据文件销毁，再创建成功备份。该失败不是绕过项，而是首次管理员秘密生命周期与备份安全门槛生效的证据。
