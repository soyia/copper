# Copper 一站式安装与维护入口 v0.4.5（内部演练）

> `INTERNAL_REHEARSAL_ONLY`：本安装器和配套介质只用于内部安装演练，不构成正式发布或客户交付。
>
> `FORMAL_RELEASE_BLOCKED`：既有 M6 平台历史、权利、安全、外部专业复核和实体延期项仍须在正式发布前关闭。

## 1. 这版解决什么问题

过去的安装需要操作者解压、切换目录、逐张导入运行文件、手工编辑配置、复制摘要并判断证书状态。一个字符、换行或目录错误就会使安装中断，而且不容易判断是否可以重试。

安装阶段把这些动作收进同一个入口。Mac 操作者优先运行：

```bash
./copper-install-from-mac
```

它会在 Mac 本地生成或复用恢复密钥、制作第二份私钥副本、检查 DNS/SSH、只上传校验清单中的安装文件，并在 Ubuntu 上自动启动安装。私钥不会进入安装答案、介质上传目录或服务器。

如果完整介质已经位于 Ubuntu 服务器，则运行：

```bash
sudo ./copper-install
```

安装器会先完成所有能够提前完成的检查，再显示完整计划。只有操作者输入确认文字后，才会创建配置、随机密钥、数据目录和服务。

## 2. 面向普通使用者的输入

Mac 入口会依次询问并确认：

1. 站点代号：用于识别这套 Copper 和它的备份，例如 `copper-shop-a`；
2. 访问地址：可填写域名或本机固定公网 IPv4，例如 `18.142.134.26`，也可粘贴 `https://` 开头的地址；安装器会去掉协议和末尾斜杠，不接受 `http://`、端口、登录路径或参数。IP 必须与服务器公网 IPv4 一致；私网、回环、共享地址、多播、保留地址和 IPv6 均不作为此版本的安装目标；
3. 服务器公网 IPv4：例如 `18.142.134.26`；
4. 服务器登录用户名和 SSH 私钥位置；登录用户名会单独询问，默认 `ubuntu`，也可填写镜像实际使用的 `ec2-user` 等账号，不再静默假定服务器一定使用 `ubuntu`；
5. 本机主恢复私钥目录和第二份副本目录。第二份推荐位于外接盘；若同盘，只能明确标记为内部演练。

登录用户名可配置不代表放宽服务器系统要求；当前候选仍只支持 Ubuntu Server 24.04 x86_64。使用 `ec2-user` 等自定义账号时，目标机本身仍须通过后续 Ubuntu 环境检查。

Mac 入口自动调用离线密钥工具生成 `age1` 公钥，并把两份私钥逐文件校验。重复运行时复用已有且完全一致的密钥，不覆盖、不换钥。产品版本、三项运行文件、固定目录和安全默认值均从已校验介质读取，不再要求用户复制摘要、上传目录或编辑 `/etc/copper/copper.env`。

## 3. 写入前检查

安装器在写入前逐项检查：

- 是否使用 `sudo`；
- 是否为 Ubuntu Server 24.04 x86_64；
- 是否至少有 2 CPU、4 GiB 内存和 20 GiB 可用磁盘；
- 安装介质是否完整，所有文件的 SHA-256 是否一致，是否混入未校验文件；
- 80/443 是否被其他软件占用；
- 已有 Docker 是否符合版本；没有 Docker 时是否能访问官方安装源；
- 域名格式、公网 IP 格式、备份公钥格式是否正确；
- 域名的全部 IPv4 是否只指向填写的服务器 IP；直接使用固定公网 IPv4 时核对地址一致，不依赖 DNS；
- 是否残留会把部分用户引向其他主机的 IPv6（AAAA）记录；
- 是否检测到来源不明的数据目录、不同产品版本或非受管配置。

系统、介质、数据边界等硬问题会安全停止，不会自动关闭别的软件、覆盖不同版本或删除数据。

### DNS 尚未生效时

DNS 不一致不会立刻把用户赶出安装流程。页面会给出三个选择：

1. `我已设置好，重新检测`：修改 DNS 后原地再次检查；
2. `更换域名或服务器 IP`：在同一安装中重新输入并检测；
3. `暂时退出，稍后再运行`：尚未写入配置，之后重新运行即可。

只有解析结果全部符合要求，安装器才显示最终计划。

固定公网 IPv4 模式自动使用正式 `COPPER_TLS_MODE=ip` 入口，以介质内锁定版本和 SHA-256 的
ACME 客户端申请可信短期证书，并启用每日续期。安装器先把客户端持久保存到 `/opt/copper/offline/`，
安装后无需保留临时介质路径；TCP 80 必须持续可供 HTTP-01 校验，TCP 443 用于访问。
已有兼容 Docker 会复用；引导阶段仍可能访问 Ubuntu 软件源和证书服务，不能称为完全断网安装。

同版本修复和中断继续会保留客户 OCR、远程访问、备份策略与公钥；不同备份公钥必须走正式密钥轮换，
不能用重装静默换钥。此版本的 `change-domain` 只支持域名之间变更；涉及公网 IP 或域名/IP 模式迁移
时会在写入和服务操作前停止，原配置和证书保留。跨模式证书迁移尚未验收。

## 4. 确认后自动完成

用户确认后，安装器自动完成：

1. 原子解压精确 Deploy 版本；
2. 安装或核对 Docker Engine 29.x、Compose 5.x 和备份工具；
3. 运行主机预检；
4. 导入三项离线运行文件，并同时核对标签、不可变 ID 和 amd64 架构；
5. 从受控模板原子生成配置；
6. 生成并保留随机数据库密钥；
7. 启动 MySQL、Backend、Web，等待三层健康；
8. 申请并验证当前域名的可信 HTTPS 证书；
9. 证书通过后才生成首次管理员凭据，并形成安装报告。

安装器不会自动显示管理员一次性密码。安装完成后，在服务器运行：

```bash
sudo copper-maintain
```

选择“首次管理员登录”，菜单会按顺序提示授权管理员查看一次性密码、打开 HTTPS 登录地址、强制改密、使用新密码重新登录，并复查一次性凭据文件是否销毁。安装完成页和 `copper-install status` 都会重复显示这个固定入口。

v0.1.1 使用 Python 3.12 原生 TLS 握手完成证书链和访问域名核对，不再调用该版本已经移除的旧接口。证书不可信或域名不匹配仍会安全暂停。

v0.1.2 增加 Mac 一键远程入口和本地私钥双副本校验。直接在服务器安装时，确认文字会单独显示为：

```text
"INSTALL copper-shop-a"
```

操作者只输入双引号内的字符，不输入双引号。

v0.1.3 修正 macOS 会把仅有 IPv4 的域名显示成 `::ffff:IPv4`、从而被误判为真实 IPv6 记录的问题。真实 AAAA 记录仍会被检测并阻止错误安装。

v0.1.4 把安装介质改为逐文件上传。连接中断时每个文件最多自动尝试 3 次，并通过 SFTP 从远端已完成位置继续；上传完成后逐文件和整份清单两次校验。重新运行相同介质时会复用稳定的远端暂存目录，完整文件直接跳过，未完成文件继续传输。

v0.1.5 修正首次上传时错误使用续传参数、导致远端文件不存在便连续失败的问题：首次上传先创建文件，产生半文件后才切换为断点续传。确认安装计划后，Mac 会在当前用户的 `~/Library/Application Support/Copper Installer/unfinished-install.json` 保存权限为 `600` 的未完成会话；只记录域名、服务器、站点及本地路径，不保存 SSH 私钥内容、age 私钥内容或密码。再次运行时可选择继续、重新填写或暂时退出。

v0.1.6 允许用户在“访问域名”中直接粘贴 `https://`开头的安全访问地址，安装器会自动提取域名；为避免误安装，`http://`、端口、路径、参数和带账号的地址仍会停止并给出易懂提示。

v0.2.0 增加安装后固定入口：服务器运行 `sudo copper-maintain`，Mac 运行 `./copper-manage-from-mac`。Mac 安装成功后保存权限为 `600` 的站点维护记录，只保存站点、服务器、SSH 私钥路径和本机密钥目录，不保存任何私钥内容或密码，并默认询问是否立即进入后续向导。数据保护入口复用这些信息，自动完成交接登记、加密备份、下载及侧车校验、客户私钥离线验证、第二位置复制、验证回执登记和每日计划；恢复入口只做隔离旁路演练，不提供一键覆盖正式数据。

v0.2.1 增加安装完成强制复查。服务器残留其他站点、其他安装器版本、其他产品版本、其他 Deploy 提交、旧安装状态、断开的系统入口或来源不明发布目录时，安装器会明确停止，不再把旧 `COMPLETE` 记录当成本次成功。安装结束只有同时核对站点身份、`copper-install`、`copperctl`、`copper-maintain`、MySQL/Backend/Web 健康和可信 HTTPS 后才返回成功；Mac 端只有通过同一组远程后验收才保存站点记录和进入首次登录。

v0.2.2 修正 Mac 端远程安装边界脚本在读取旧状态后可能错误返回非零的问题。旧站点或旧版本现在会在生成客户密钥和上传介质之前给出明确拒绝，不再退化为“无法核对服务器”的模糊提示。

v0.3.0 增加完整退场向导。普通卸载停止服务但保留数据库、图片、配置、密钥和备份，并可用同一介质重新启用；彻底移除会创建新的加密一致性整站备份，停止新的业务写入，下载并离线验证，复制到第二位置，把精确备份与客户回执登记到服务器，再要求输入站点代号。成功后删除服务器站点数据、安装程序和 Copper 运行残留，在 Mac 与第二位置保存卸载回执；Ubuntu、Docker、SSH、DNS、客户恢复私钥和已下载备份保持不变。

v0.3.1 修正闭集介质的离线镜像摘要口径。介质生成时不再信任来源文件中可能记录的构建机 config digest，而是逐一打开 Web、Backend、MySQL 的 OCI 归档，验证唯一标签、manifest、config 对象和 amd64 架构，再把 Docker 29 导入后使用的 manifest digest 同步写入安装参数、发布清单和平台证据。安装器仍严格拒绝摘要不一致，不会为了继续安装而放宽完整性门槛。

v0.3.2 收口安装后的生命周期稳定性。整站备份恢复三层服务后必须连续三次通过健康观察才会返回菜单；Mac 操作者明确选择删除隔离恢复后，会把完整的 `DISCARD + 恢复编号` 作为受控确认交给服务器，不再要求重复输入，但正式数据切换和回滚仍必须在可信交互终端人工确认。恢复演练会保存 root 之外、仅当前 Mac 用户可读的中断记录，下次进入同一菜单先清理上次旁路，不会盲目新建并撞上 18080 端口；同时补齐 `copperctl stop`，使“最新备份后停止写入、离线验证、再永久删除”的流程不再调用不存在的命令。下载、离线验证或第二位置复制失败时会自动恢复正式站点；任一稳定、确认或停机门槛失败，正式站点数据和本地卸载证明均保持不变。

v0.3.3 修正恢复私钥目录重复追加站点代号的问题。主副本和第二副本都可填写共享上级目录，也可直接填写已经以站点代号结尾的最终目录；安装计划会先显示规范化后的真实落盘位置，最终目录不存在时直接创建该目录，不再生成 `站点代号/站点代号`。原有双副本一致性、不同文件系统提示和私钥不上送门槛保持不变。

v0.4.0 增加“从整站备份恢复已删除的站点”独立入口。Mac 会从停用站点记录中找到对应卸载回执，严格核对主位置与第二位置的客户恢复私钥、整站备份、`.sha256`、离线验证回执和服务器验空证明；随后引导恢复到原服务器或另一台全新 Ubuntu 服务器。程序自动完成空白安装、临时管理员改密门槛、客户公钥登记、备份传输、客户私钥离线复验和 `127.0.0.1:18080` 隔离旁路恢复。

普通恢复演练仍然只允许旁路验证和删除，不包含正式切换。灾难恢复入口在旁路达到 `VALIDATED` 后，仍由操作者在可信交互终端输入服务器显示的精确 `SWITCH` 确认文字；切换后必须使用备份时的管理员密码登录并核对关键数据。切换前的空白站点会保留为回滚点，程序不会在未再次确认时自动删除。中断记录只保存非秘密目标信息和证据摘要，不保存 SSH 私钥内容、age 私钥内容或密码；重新进入会从已完成步骤继续。

v0.4.1 将灾难恢复收口为同一个本机入口。安装目标机前先用客户私钥解密备份，并核对备份中的 Web、Backend、MySQL 精确版本与当前介质一致；不一致时在修改服务器前停止。切换成功后不再过早执行“可恢复”检查，操作者只需在浏览器确认数据正确，程序随后自动创建恢复后的首份一致性备份、下载、校验侧车、离线解密验证、复制到第二位置、登记回执、启用每日计划，最后执行系统自检和监控并生成双位置恢复回执。中途退出后从已完成阶段继续，不会因为收尾检查失败把已经成功的切换误报为未切换。

v0.4.2 增加现有站点的一键离线升级。Mac 管理菜单选择“升级 Copper”，再选择发布方提供的标准离线升级目录或 `.tar.gz` 和独立完整校验码。程序会先在 Mac 核对闭集文件、大小和 SHA-256，再断点续传到服务器；服务器仍使用既有的 READY、升级兼容表、升级前一致性备份、隔离迁移、数据总量/附件/外键核对和原子切换，不另造第二套数据库升级规则。

切换仍要求操作者在可信终端输入服务器显示的完整确认文字；切换后使用原管理员账号和原密码登录核对数据。确认正确后，程序自动创建升级后的新整站备份，下载、离线解密验证、复制到第二位置并登记回执。只有该新备份完成客户离线验证，服务器才允许“接受升级”并释放旧版本回滚副本；接受前可以随时保留旧副本或人工回滚，接受后下一次升级才会解锁。网络中断时本机只保存站点、升级版本、发布索引摘要、非秘密路径和步骤，不保存 SSH 私钥内容、客户恢复私钥内容或密码；重新进入会按服务器真实状态继续，不重复准备或迁移。

v0.4.3 降低首次安装和后续升级的重复传输。Mac 首次安装上传前先逐张核对服务器 Docker 中的 Web、Backend、MySQL 不可变内容 ID 和 amd64 架构；完全相同的组件直接复用，不再上传对应归档。只要摘要、架构或可读性任一不一致，仍会上传并重新校验，不能用“服务器装过 MySQL”替代精确身份检查。真正空白且不能联网的服务器仍需要从完整介质取得三张镜像。

升级发布新增 `copper-upgrade-delivery/v1` 组件差异包。发布方把来源离线索引与目标发布清单逐项比较，只把内容 ID 发生变化的 Web、Backend、MySQL 放入镜像归档；未变化组件在索引中明确标为 `reuse`。目标服务器必须同时满足来源产品版本、当前运行镜像 ID 和 amd64 架构三项精确匹配，否则拒绝拼接并提示改用匹配的差异包或完整包。数据库业务数据始终通过一致性备份、Flyway 迁移和隔离恢复验证升级，禁止对 MySQL 数据目录做文件级或二进制差分。

恢复过程中只保留三类人工确认：确认恢复计划、切换前确认知道备份时的管理员密码、切换后在浏览器确认关键数据。空白站点的首次管理员密码只是切换前的临时安全入口，不会改写备份内的管理员账号或业务数据。失败的隔离旁路可以由入口清理后重试；正式数据的切换与回滚仍保留服务器可信终端的精确确认文字。

v0.4.4 补齐不同云镜像的登录账号兼容：首次安装会明确询问服务器登录用户名并在最终计划中再次显示，默认值仍为 `ubuntu`；无人值守演练必须显式提供用户名，避免把非 Ubuntu 默认账号静默连错。整站灾难恢复同时改为复用安装入口已经验证的介质参数读取能力，不再调用不存在的解析函数；恢复仍先完成备份与当前介质三项精确镜像核对，核对失败或参数缺失时不会修改目标服务器。

v0.4.5 把 Cloudflare 可选远程访问纳入既有 Mac 一站式维护菜单。操作者先选择站点，再选择“互联网远程访问（Cloudflare，可选）”，后续首次配置、启用验证、状态、Token 轮换、停用和本地移除全部复用服务器同一菜单；普通用户不再复制底层 `copperctl` 子命令。移除仍绑定当前站点并二次选择，保留 Copper 数据、图片和备份；Cloudflare 云端资源继续由客户账号显式清理。

2026-07-21 的内部演练已使用 v0.4.4 从一份经过双位置和离线验证的已删除站点备份完成空白安装、旁路 `VALIDATED`、正式切换、恢复后新备份、离线复验、第二位置复制、每日计划及最终自检，过程中没有再触发 `parse_env` 异常。该证据只证明灾难恢复子链；由于入口继续了旧检查点中的 `ubuntu`，服务器登录用户名的新提示仍须由下一份全新安装样本直接验收。

同日增加 `scripts/m7-02-operator-simulation.py`，用于在不修改真实站点、不启动浏览器或容器的前提下连续模拟登录用户名输入、DNS 原地重试、换域名和失败清场。运行 `python3 scripts/m7-02-operator-simulation.py --output <回执路径>` 可得到 `copper-m7-02-operator-simulation/v1` 回执；该回执只用于内部工程回归，不能替代正式发布前的真实非开发客户独立安装样本。

正式双人交接仍要求客户确认人与独立见证人真实签署。内部演练身份会显著标记 `NOT-FORMAL`，不能成为正式客户签署结论。Mac/U 盘按需复制也不等于无人值守异机备份；NAS/S3 目标和异机告警仍需客户提供真实地址与凭据后验收。

## 5. 证书失败时怎么处理

程序容器健康不等于用户已经可以安全访问。只要可信 HTTPS 尚未通过，安装状态就停在 `等待安全访问证书`，不会宣称安装完成，也不会建议改用不安全的 HTTP。

安装器会尽量把原因翻译为普通语言：

- DNS 尚未生效；
- 公网无法连接 80/443；
- 同一域名短期重复申请次数过多；
- 证书仍在等待签发。

如果日志包含证书服务给出的可重试时间，安装器会转换为本地时间。到达该时间前，`continue` 只检查证书是否已经可用，不会再次重启并重复申请。

固定入口：

```bash
sudo copper-install status
sudo copper-install continue
sudo copper-install change-domain
```

`change-domain` 会先检查新域名和 IP，再原子备份配置和重启服务。若原域名本来可用而新域名证书失败，安装器自动恢复旧域名，避免把可用站点改坏。

## 6. 重复执行和修复边界

| 场景 | 入口 | 结果 |
| --- | --- | --- |
| 全新安装 | `sudo ./copper-install` | 写入计划后逐阶段完成 |
| 安装中断 | `sudo copper-install continue` | 从受控记录继续，保留已完成阶段 |
| 同版本修复 | `sudo copper-install repair` | 重新核对运行环境、介质、配置和服务，保留数据与随机密钥 |
| 查看进度 | `sudo copper-install status` | 显示当前阶段、最近提示和下一步 |
| 更换域名 | `sudo copper-install change-domain` | DNS 通过后受控修改，失败可回退旧域名 |
| 已彻底移除后整站恢复 | Mac `./copper-manage-from-mac` -> “从整站备份恢复已删除的站点” | 核对双位置证明与程序版本，恢复到原服务器或另一台全新服务器；确认数据后自动完成新备份、下载、离线验证、第二位置复制、每日计划和回执，保留回滚点 |
| 已安装站点升级 | Mac `./copper-manage-from-mac` -> “升级 Copper” | 核对离线发布包和独立校验码，断点上传，升级前备份，隔离迁移，人工切换；确认数据后自动完成升级后备份与离线验证，再人工接受升级并释放旧回滚副本 |
| 已经完成后再次运行安装 | `sudo ./copper-install` | 识别为已完成，不重复初始化 |
| 不同版本 | 普通安装入口 | 拒绝覆盖；必须从 Mac 管理菜单选择“升级 Copper”并使用标准升级包 |
| 来源不明的已有数据 | 任意安装入口 | 拒绝覆盖，要求先备份和确认来源 |

普通安装、继续和修复仍没有“覆盖安装”或“恢复出厂”。v0.4.0 的彻底移除和灾难恢复分别位于 Mac 的独立危险流程中：删除必须绑定服务器最近一次成功备份、客户离线验证回执和第二位置副本；恢复还必须绑定卸载回执与服务器验空证明，并在旁路验证后由操作者人工切换。两者都不能从普通安装按钮绕过。

## 7. 可重复验收输入

真实操作者使用交互输入。自动化验收可以使用只含非秘密信息和客户公钥的 JSON：

```json
{
  "siteId": "copper-internal-test",
  "domain": "copper-test.example.com",
  "publicIp": "203.0.113.10",
  "backupPublicKey": "age1...",
  "timeZone": "Asia/Shanghai"
}
```

```bash
sudo ./copper-install install --answers /安全位置/install-answers.json --yes
```

`--yes` 必须与 `--answers` 同用，不能单独跳过人工确认。答案文件不得包含密码、Cookie、令牌或私钥。

## 8. 状态与审计文件

以下文件均为 root-only `0600`：

- `/var/lib/copper-installer/install-plan.json`：用户确认的非秘密安装计划；
- `/var/lib/copper-installer/state.json`：当前阶段、最近错误、证书重试时间；
- `/var/lib/copper-installer/install-report.json`：成功后的无秘密安装报告。

安装记录刻意放在业务数据目录 `/var/lib/copper` 之外，避免首次主机预检把安装器自己的进度误判为未知客户数据。配置仍位于 `/etc/copper/copper.env`，但普通安装过程不再要求用户手工编辑。随机密钥继续由现有 Copper 密钥文件管理；安装记录不保存密码、私钥或首次管理员凭据。
