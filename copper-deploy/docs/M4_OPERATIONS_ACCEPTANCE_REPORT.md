# M4-05 日志、RPO/RTO 与故障处置验收报告

验收日期：2026-07-15（Asia/Shanghai）

## 结论

M4-05 已通过全仓合同、Ubuntu 24.04 x86_64 真实容器、日志轮转、MySQL 日志策略、容量阻断、RPO 证据和六类故障清单验收。Copper 现在对应用、网关、数据库、审计和运维日志分别给出上限、权限、保留和安全删除规则；`copperctl operations status` 能区分本机恢复点、整机损失恢复点、完整恢复演练、工程目标和商业 SLA。

本轮没有把单次脚本耗时冒充 RTO，也没有把本机备份冒充整机容灾。最终验收站只配置 `local`，因此新鲜备份显示本机 `TARGET_MET`，整机损失明确显示 `NOT_SUPPORTED`，总体为可解释的 `WARNING`。这正是责任边界生效，不是未完成项。

M4-05 没有执行真实数据库中断、真实磁盘耗尽、证书过期或异常断电；这些破坏性故障及恢复后的经营财务不变量复核属于 M4-06。

## 实现范围

- `copperctl` 升级到 `0.9.0-m4`，新增 `operations status [--json]` 和 `operations checklist <fault> [--json]`。
- `config/operations-policy.json` 固化日志、容量、RPO/RTO、服务模型和六类故障处置的机器可读合同。
- Web/Caddy、Backend 控制台和 MySQL 使用 Docker `local` 日志驱动，每服务 `20 MiB × 5`。
- Backend 文件日志显式设置单文件 20 MiB、最多 7 天、总量 200 MiB，启动时清理超过策略的旧滚动段。
- 单机基线关闭 MySQL binlog、general log 和 slow log。当前产品没有基于 binlog 的归档/PITR，禁止让无恢复用途的日志无限增长。
- 备份、监控、恢复和升级 JSONL 事件流均按 5 MiB 轮转，只保留当前和上一段；目录/文件继续使用 `0700/0600`。
- 备份和监控 systemd 服务增加每 30 秒 200 条的日志速率上限；每日备份随机偏移固定，使健康主机的相邻计划间隔保持 24 小时。
- 保留既有后端容量强制规则：严重时阻止新导出、备份和大附件；阻断时拒绝全部业务写入；数据库、附件、审计、唯一成功备份和唯一回滚证据不自动删除。
- 六类清单覆盖数据库、磁盘、备份、证书、时间和异常断电，每类都有停止规则、诊断命令、恢复门槛和升级路径。

## 实机场景

### 1. 实际日志合同

- MySQL、Backend、Web 三个运行容器的 `HostConfig.LogConfig` 均为 `Type=local`、`max-size=20m`、`max-file=5`。
- Backend 运行环境实际包含 `MAX_FILE_SIZE=20MB`、`MAX_HISTORY=7`、`TOTAL_SIZE_CAP=200MB`。
- MySQL 实际查询 `@@log_bin / @@general_log / @@slow_query_log` 为 `0 / 0 / 0`。
- 使用同一 Docker `local` 驱动创建一次性 1 MiB × 2 轮转探针并输出 8 MiB；驱动目录实际占用 1,863,078 字节，证明旧段被轮转压缩而非按原始输出无限增长。探针随后删除。

### 2. 恢复点证据

- 首次管理员完成改密且一次性凭据销毁后，创建真实一致性加密备份并通过外层、envelope、密文载荷和离线私钥证明。
- 最近成功备份年龄约 0 小时，本机恢复点为 `TARGET_MET`。
- 仅配置 `local`，整机损失恢复点为 `NOT_SUPPORTED`，没有错误宣传异地容灾。
- 本轮没有新增完整恢复切换，因此恢复演练为 `NO_FULL_DRILL`；240 分钟技术目标仍引用 M2/M3 实测，标记 `commercialSla=false`。

### 3. 容量保护

- 正常空间为 `NORMAL`。
- 仅在 `COPPER_TEST_MODE=1` 注入 512 MiB 可用空间观测，不真实填满磁盘；`operations status` 返回总体和容量 `BLOCKED`、退出码 1。
- 输出明确严重级停止大任务、阻断级停止业务写入，不提供删除数据库/附件/审计/唯一备份的捷径。

### 4. 故障清单与 systemd

- database、disk、backup、certificate、time、power 六类 JSON 清单全部包含停止规则、诊断命令、恢复门槛和升级路径。
- 备份与监控 service/timer 在隔离复制中通过 `systemd-analyze verify`；没有写入或启用主机正式 unit。
- `FixedRandomDelay=true` 和 service 日志速率上限均在候选资产与实机校验中通过。

## 失败安全与清理

首次实机尝试暴露 `operations.py` CLI 未把已加载策略传给采集函数，验收在读取状态前失败并自动清理隔离栈；增加 CLI 回归用例后重跑。第二次全部运行场景已通过，但隔离 systemd 校验错误引用主机不存在的正式命令路径；改为复制 unit 并只在临时目录绑定候选命令后通过。两次均未改正式 systemd、8191 或客户数据，也未把未完成结果算作成功。

最终：

- 隔离 MySQL、Backend、Web、一次性轮转探针、Compose 网络、运行配置、测试数据库、备份、证书私钥、age 私钥和管理员 Cookie全部删除；
- 18108、18099 和 8191 均无本轮监听；
- 两次失败证据和服务器 `/tmp` 候选已删除；
- `/opt/copper-m4-05` 只保留最终 root-only 脱敏证据；根盘仍约 38 GiB 可用。
