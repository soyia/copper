# 小微商贸轻量经营能力规格

> 状态：内部产品与验收规格
>
> 适用对象：小微铜材经销商、个人经营者
>
> 原则：复用现有采购、库存、销售、资金和批次事实；默认不增加日常必填步骤，不建设重型 WMS、制造、通用审批或平台能力。

## 1. 产品边界

本能力包解决八类高频经营问题，但不改变 Copper 的主流程：

`采购 → 入库 → 库存 → 销售 → 出库 → 应收应付 → 收付款 → 对账`

所有辅助能力遵守以下规则：

- 主流程能够独立完成；报价比较、质保书、交付跟踪、分享和开放接口均为按需使用，不成为开单、发货、收付款或关账的强制前置。
- 建议只读取现有事实并说明算法，不自动创建采购单、修改销售单、移动库存、登记收付款或生成核销。
- 已确认事实发现错误时使用冲正、作废、重开或追加事件，不直接覆盖库存、成本、应收应付和资金历史。
- 手机端优先复用同一套权限与页面，不单独建设角色应用，也不以“切换角色”代替授权。
- 没有真实第三方凭据和正式接口时，只提供受控文件导入入口，不伪装成银行、税务或物流直连。

## 2. 八项能力矩阵

| 能力 | 经营问题 | 最短操作 | 权威事实与状态 | 明确不做 |
| --- | --- | --- | --- | --- |
| 其他出入库 | 送样、领用、正常损耗和零星其他出库不能继续写备注或直接改库存 | 使用独立列表与主从表单；一张单据可增加多个商品明细，每项独立选择有自由库存的批次并逐包装填写扣取量，本项数量自动合计 | 独立单号；实际领用人、经办人/发放人、系统制单人分别记录；先保存草稿，实物交付时确认发放并立即逐项扣减库存、结转成本和过账，随后由实际领用人签字并上传原件归档；已发放待签字或已归档只允许填写原因后冲正 | 不借用销售出库，不产生销售履约或应收；不做领料工单、生产耗用、复杂审批 |
| 补货与库龄建议 | 老板不能快速判断哪些货该补、哪些货压库 | 打开经营助手查看建议，无需维护第二套库存参数 | 现存、草稿占用、在途采购、近 30 天出库、供应交期和最老批次 | 不自动下采购单，不承诺预测准确，不做高级需求计划 |
| 销售贡献 | 销售额不等于赚到的钱，零星运费等费用又容易重复登记 | 在销售订单或直接出库详情查看；需要时把已有费用源单归集过来 | 已出库收入、实际批次成本、已有费用源单分配和未收金额 | 不重录付款，不把费用分配当会计凭证，不做复杂成本中心 |
| 移动工作台与扫码 | 老板和仓库在手机上查看经营提醒、出库找批次操作慢 | 响应式经营助手；出库扫描已配置包装条码后带出商品和可用批次，仍由人确认 | 同一登录、同一权限、同一库存批次；扫码只是输入助手 | 不做独立 App、离线自动过账、无人复核扣库存 |
| 批次质保 | 客户索要质保书时找不到对应批次，错证又无法追溯 | 从库存批次按需登记、复核或作废 | 批次、证书号、供应商/厂家批号、炉号、卷号、复核状态和历史 | 不成为所有入库必填，不做实验室管理 |
| 交付签收 | 出库以后只靠微信追踪，异常和签收没有统一记录 | 在已出库单登记交付，依次确认发出、签收；异常可登记并重开 | 出库单下的交付状态与追加式事件 | 签收不等于收款或核销，不做线路调度和运力平台 |
| 采购报价比较 | 电话、微信里的几家报价难以在采购草稿旁比较 | 草稿中录入少量供应商报价，按合计、运费、交期和结算条件选择 | 报价快照、选择人、选择时间和作废原因 | 不静默改采购草稿，不做招投标、采购申请和多级审批 |
| 单据协同与数据接入 | 客户/供应商需要看单据，外部系统又不能获得全库权限 | 生成短期只读链接；按往来单位签发只读订单密钥；文件进入现有导入预检 | 令牌只显示一次且只保存摘要；链接可到期/撤销；API 限定往来单位与 `order.read` | 不暴露库存成本、往来余额和内部备注，不开放写接口，不假装完成第三方直连 |

## 3. 计算口径

### 3.1 补货与库龄

- 可用库存 = 当前实际结存 − 未确认出库草稿占用。
- 在途采购 = 已确认且未完成采购订单的未到数量；草稿采购不计入。
- 近 30 天日均出库 = 最近 30 个自然日已确认出库数量 ÷ 30。
- 默认目标天数 = 已发布供应交期 + 14 天安全期；没有供应交期时使用 7 天。
- 建议量 = `max(日均出库 × 目标天数 − 可用库存 − 在途采购, 0)`。
- 最老可用批次达到 180 天且无需补货时标记库龄关注。近 30 天没有出库时只提示消化库存，不建议自动补货。

这些参数是透明的首版统一口径，不要求小商户逐商品维护。后续只有出现稳定、可证明的差异需求时，才考虑提供少量覆盖配置。

### 3.2 销售贡献

- 销售订单收入只取其已确认出库单金额；未出库订单不提前算收入。
- 直接出库收入取已确认直接出库金额。
- 库存成本取出库时冻结的实际批次成本，不使用当前商品参考成本回算历史。
- 贡献毛利 = 已出库收入 − 库存成本 − 已分配销售相关费用。
- 费用分配只能引用已确认的企业费用或其他费用源单，累计分配不得超过源单金额；撤销分配不修改源单、付款、凭证和总账。

## 4. 状态与纠错

| 对象 | 正向状态 | 纠错方式 |
| --- | --- | --- |
| 其他出入库 | 草稿待发放 → 已发放待签字 → 已签字归档 | 实物发放时立即扣减库存并过账；签字归档不得重复扣库；已发放待签字或已归档均可填写原因冲正，反向恢复数量、成本、包装和过账事实 |
| 采购报价 | 可选 → 已选用 | 草稿期间可改选；不再使用时填写原因作废 |
| 费用分配 | 有效 | 填写原因撤销，原费用源单保持不变 |
| 交付 | 待处理 → 已发出 → 已签收 | 待处理/已发出可记异常；已签收或异常填写原因后重开 |
| 质保书 | 待复核 → 已核验/已驳回 | 错证走作废并保留复核历史，不原地覆盖已复核结果 |
| 分享/API 密钥 | 有效 | 到期自动失效；需要提前停用时填写原因撤销 |

## 5. 权限与隐私

- 仓库岗位可办理其他出入库和交付；采购岗位可维护采购报价；销售岗位可维护交付、销售费用归集和本人有权单据的分享。
- 经营汇总只对具有完整单据、往来单位、商品和仓库数据范围的角色开放，避免把局部数据包装成全局经营结论。
- 质保书按批次和往来单位数据范围校验；成本字段继续受库存成本权限控制。
- 公开分享只返回订单号、往来单位名称、业务日期、状态、价税口径、金额和商品行，不返回内部备注、库存成本、欠款、联系方式或系统账号。
- 开放 API 密钥限定一个往来单位、只读订单范围和最长一年有效期；明文只在创建时展示一次。

## 6. 内部验收要求

- V1 到本次迁移必须在空白 MySQL 8.4 数据库完整执行。
- 送样、领用或损耗草稿采用单据头加多商品明细；每项商品的数量必须由该项各来源包装扣取量自动合计，不得把 kg、件、箱等不同库存单位强行汇成一个数量。库存变化时点是实物实际发放：确认发放后立即逐项扣库并进入“已发放待签字”，签字附件后续上传归档且不得再次扣库。月结前必须补齐实际领用人签字；确认发放、签字归档和冲正后，各明细及来源包装必须显示办理时的扣前、扣取、扣后数量并可由不可变流水复算。入库详情保留原始入库数量，同时单独显示对应批次的当前账面结存、草稿占用、自由可用量及已发放/已冲正的非购销扣取记录，不能把历史入库数误当当前库存。
- 补货建议必须可由数据库事实复算，且不得产生采购订单写入。
- 费用归集与撤销前后，费用源单、资金、应收和会计事实不得被改写。
- 交付签收前后，应收、已收和核销金额必须保持不变。
- 质保书复核必须保存不可变历史，错证只能作废。
- 分享和开放 API 必须验证过期、撤销、令牌摘要及往来单位越权阻断。
- 前端必须完成生产构建，并在隔离浏览器验证桌面和窄屏下的经营助手、扫码输入、批次操作及订单详情面板。

## 7. 四项日常协同补充

这四项只补经营者每天会遇到的“等回复、等到货、等回款、等录单”，不增加采购、销售、仓库和财务主流程步骤，也不建设重型门户、供应链计划或通用 OCR 平台。

| 能力 | 使用入口与最短动作 | 保存的事实 | 明确边界 |
| --- | --- | --- | --- |
| 对外确认 | 在报价、客户应收对账或销售交付详情生成短期链接；客户选择内容无误或存在差异 | 冻结 JSON、SHA-256、有效期、查看次数、确认人、手机尾号、结论、留言和时间 | 确认不等于收付款、核销、开票、签收或可靠电子签名；不改变原单据 |
| 采购跟催 | 在普通采购订单内追加供应商已发、预计到货变更、延误、异常和解决 | 采购单及明细、每次发出数量、预计日期、物流、原因、操作人和时间 | 已发不等于入库、库存或应付；直运继续使用直运交付链，不重复维护 |
| 现金窗口 | 在经营助手查看未来 7 天和 30 天，必要时点回来源单据 | 总账现金/银行期初、已确认应收应付和资金支出、到期日、来源单号、保守与按账期余额 | 只读，不创建资金计划；应收只是预计流入。保守口径假设未来回款均未到，避免老板把欠款当现金 |
| 单据识别 | 上传供应商报价单、磅单或签收单；下载原件核对候选值后确认或驳回 | 原文件、文件摘要、提取方式、候选字段、置信度、人工确认值、复核人和说明 | 候选确认后仍不创建采购报价、入库、库存、交付、应收应付或收付款 |

### 7.1 状态和纠错

- 对外确认包为 `有效 → 内容无误/存在差异`；提交后不可覆盖。尚未确认的链接可填写原因撤销，到期后失效。需要重新确认时生成新的冻结包。
- 采购跟催采用追加事件，不回写或删除旧事件。分批发出按采购明细累计且不得超过采购数量；异常解决要追加解决记录。
- 现金窗口每次打开从当前权威事实重算，不保存一套可被人工修改的预测余额。来源缺少明确到期日时必须说明采用的保守日期口径。
- 单据识别批次为 `待确认 → 已确认候选/已驳回`。已复核结果不可原地重写；原文件和 SHA-256 保留用于审计，同一类型同一文件不得重复上传。

### 7.2 数据和安全

- 外部确认令牌只在生成时显示，数据库只保存 SHA-256；公开页面不返回内部备注、采购价、成本、毛利、库存、账号和完整联系方式。
- 客户对账冻结范围来自服务端全部符合条件的应收事实，不允许把分页列表相加冒充全量余额。
- 采购跟催、外部确认和单据候选分别使用独立细粒度权限；现金窗口沿用经营汇总权限与数据范围。
- 原文件进入既有附件存储和业务导出；整站恢复必须同时覆盖六张新增表、外键、确认快照和原文件。

### 7.3 额外验收

- 客户完成报价、对账或交付确认前后，库存、应收应付、收付款、核销、发票、凭证和总账必须保持不变。
- 采购登记分批已发、预计到货、延误和异常前后，库存、入库数量、应付和付款必须保持不变。
- 7 天/30 天每天的预计流入流出、保守余额和按账期余额必须可由来源单据逐笔复算，且不能从有限分页结果汇总。
- 文本 PDF、文本文件和无文本图片均能形成待确认批次；无文本图片不得伪造识别结果，人工确认后仍不得写入正式业务表。
- V1 至当前迁移必须在空白 MySQL 完整执行，新增表、外键、业务导出与逻辑恢复逐项核对。

## 8. Mobile Fast Lite 手机快速办事

Mobile Fast Lite 不是另一套 App，也不复制客户、商品、库存、应收、资金或权限。它是同一 Web ERP 在窄屏下的专用壳层，只保留小微铜材经销商外出和现场最常用的五个短流程。

| 入口 | 最短操作 | 服务端权威结果 | 明确边界 |
| --- | --- | --- | --- |
| 查货 | 搜 SKU、商品、规格、批次、仓库，或扫描包装码 | 读取当前库存批次的实存、预留、自由可用和在途数量 | 只读；页面缓存不是库存事实 |
| 报价 / 下单 | 选择客户、地址和商品，填写数量、单位和单价，选择保存报价草稿或销售订单草稿 | 复用客户税务设置、商品包装换算和原报价/销售订单接口 | 只保存草稿；不确认、不占库存、不产生应收、不开票 |
| 收款 | 选择客户、真实到账金额、日期、结算方式和可选核销分配 | 复用原回款与多单核销接口，资金到账和核销关系分层保存 | 不伪造到账；断网不排队补记；没有成功提示必须先核对 |
| 扫码盘点 | 先选仓库，扫码定位批次，人工填写实盘数量和差异原因 | 复用库存盘点草稿接口，保存时冻结账面快照 | 扫码不自动增加数量；保存草稿不改变库存；正式确认仍走原详情校验 |
| 拍照归单 | 先选原业务单，再拍磅单、签收单或回单并确认上传 | 复用业务附件接口，保存原文件、SHA-256、上传人、时间和分类 | 照片不能创建采购、入库、交付、应收、收款或会计事实 |

### 8.1 登录、权限和设备边界

- 手机与电脑版使用同一登录会话、角色权限和数据范围；手机首页只显示当前账号有权使用的入口，不提供角色切换。
- 手机浏览器登录成功后默认进入统一手机工作台；电脑继续进入原工作台。明确的 `/mobile` 子页面返回目标可以保留，强制修改初始密码始终优先于设备分流。
- PWA 只缓存静态应用壳层，明确排除 `/api/`；不得缓存业务接口响应后冒充实时库存、欠款或资金。
- 相机扫码只是输入助手。浏览器不支持相机识码或未授权时，必须保留蓝牙扫码枪、手机键盘和手工输入退路。
- 未提交的快速报价/下单和盘点内容只在当前浏览器会话暂存；退出会话、明确保存或放弃后不得继续冒充正式业务。
- 收款、盘点草稿保存和附件上传必须在线提交并收到服务器成功结果；不建设离线队列、后台自动重试或“网络恢复即过账”。

### 8.2 Mobile Fast Lite 验收

- 390px 宽度下五个入口、表单、卡片、底部动作和相机层不得横向溢出，重要按钮触控高度不小于 44px。
- 同一账号在手机与电脑版看到相同库存数量、应收候选、往来单位、商品、仓库和业务单；越权路由仍由统一路由守卫与后端阻断。
- 快速报价和订单保存前后，库存、应收、收款、发票、凭证和总账保持不变；只有对应草稿新增。
- 扫码盘点保存前后库存保持不变；只有在原盘点详情复核并确认后才允许形成盘盈盘亏。
- 拍照归单上传前必须有原业务单；上传后可从原单据下载，并能核对原文件名、大小、SHA-256、上传人和时间。
- Service Worker 对所有 `/api/` 请求保持网络直连，不得响应缓存的业务数据。
