# M4 安全、监控、容灾与离线自主架构

> 状态：架构基线（M4-01）
> 生效日期：2026-07-14
> 适用版本：`v0.2.0-rc.1` 及后续 M4 候选版本
> 权威路线图：`docs/SELF_HOSTING_AND_DATA_CONTROL_ROADMAP.md`
> 总跟踪 Issue：<https://github.com/soyia/copper_web/issues/31>
> M4-01 Issue：<https://github.com/soyia/copper_web/issues/32>

本文冻结 M4 的安全、监控、容灾和完全离线运行边界。它是 M4-02 至 M4-07 的实现合同，不代表所列控制项已经完成；只有代码、发布物、真实故障演练和空白 x86_64 验收均通过后，路线图对应项目才可勾选。

## 1. 目标与非目标

### 1.1 目标

- 客户拥有服务器、数据库、附件、备份和恢复密钥，不依赖 Copper 官方服务才能继续经营。
- 默认保护往来单位、商品、库存、采购销售、应收应付、收付款、核销、附件和审计证据。
- 让客户独立判断系统是否可用、最后一次备份是否成功、磁盘是否危险、证书与系统时间是否正常。
- 故障必须明确成功、失败或未提交；不得向用户返回假成功，也不得在未知状态继续写业务数据。
- 恢复不以“容器启动”为完成，必须复核经营和财务不变量。
- 安全能力保持适合小微企业：默认安全、操作少、提示清楚，但不删除库存、资金、核销和审计所需语义。

### 1.2 非目标

- M4 不引入按用户、容量或功能分级的收费版本。
- M4 不建设依赖 Copper 云端的远程许可证、强制遥测或核心业务控制面。
- M4 不承诺绝对安全、零数据丢失、零停机或任意环境均可即时恢复。
- M4 不以普通应用日志替代不可变业务单据、库存流水、资金流水、核销关系或会计审计证据。
- M4-01 不实现控制项；实现、故障注入和最终验收分别由 M4-02 至 M4-07 完成。

## 2. 决策摘要

| 编号 | 决策 | 强制结果 |
| --- | --- | --- |
| M4-ADR-01 | 正式访问只经过受支持的 HTTPS 终止入口 | 宿主机不直接暴露 Backend 或 MySQL；HTTP 只用于跳转或证书挑战 |
| M4-ADR-02 | 后端是授权与审计的最终执行点 | 前端隐藏按钮不能代替接口权限、数据范围和危险操作校验 |
| M4-ADR-03 | 秘密使用文件/运行时注入并实施生命周期管理 | 秘密不得写入镜像、Git、普通日志、命令行参数或可下载诊断包 |
| M4-ADR-04 | 经营事实与安全审计分离但可关联 | 审计记录谁在何时做了什么；业务单据、库存、资金和核销记录事实结果 |
| M4-ADR-05 | 健康状态按“存活、就绪、可写、可恢复”分层 | 容器运行不等于业务可写，备份存在不等于可恢复 |
| M4-ADR-06 | 经营财务汇总由完整后端口径生成 | 禁止从前端分页、有限列表或日志估算库存和往来余额 |
| M4-ADR-07 | 故障恢复优先保护一致性，其次才是尽快恢复写入 | 无法证明一致时保持 Web 停止或只读，并要求人工处置 |
| M4-ADR-08 | 非必要外联和遥测默认关闭 | 核心业务不得依赖 Copper 官方地址或公共互联网 |
| M4-ADR-09 | RPO/RTO 按服务场景和真实演练声明 | 软件能力、自助部署、标准维护、代运维不得混为同一承诺 |
| M4-ADR-10 | 三仓和发布物共同构成安全边界 | Web、Backend、Deploy 任一缺少证据，M4 不得完成 |

## 3. 信任边界与正式拓扑

```text
客户浏览器
    |
    | HTTPS :443
    v
Caddy / 受支持的客户 TLS 终止层
    |-- 静态 Web
    `-- 同源 /api --> Backend --> MySQL 8.4
                         |            |
                         |            `-- 数据库持久卷
                         `-- 附件持久卷

受控运维入口 --> copperctl --> 配置、秘密、日志、备份/恢复、升级状态
                                      |
                                      `-- 客户本地/NAS/S3 兼容备份目标
```

### 3.1 边界规则

- 浏览器和公网均视为不可信；所有写请求必须由后端重新认证、授权和校验。
- TLS 网关只代理同源 `/api`；Backend 与 MySQL 仅在内部网络可达，不映射公网端口。
- 宿主机管理员拥有高权限，必须由客户控制 SSH、sudo、云账号、安全组和系统更新。
- 数据库、附件和备份是三个不同持久化面，容量、权限、校验和恢复状态分别监控。
- 备份目标由客户控制；服务器只保存备份接收公钥，不保存客户唯一恢复私钥。
- 第三方短信、OCR、电子发票、地图、云打印、对象存储和通知服务均在核心信任边界之外，失败必须隔离。

### 3.2 M4 最终验收环境

- 目标：AWS 新加坡区域的空白 Ubuntu Server 24.04 LTS、x86_64 主机。
- 已确认基线：2 vCPU、4 GiB 规格、50 GB 系统盘、时间同步正常、初始未安装 Docker。
- 域名：验收子域名固定为 `copper-test.pwagrowing.com`，与正式客户域名分离；源站先以 DNS-only 验证真实证书、Cookie 和同源 API，再评估代理/CDN。
- 公共文档和验收报告不得记录主机 IP、SSH 私钥路径、密码、Token 或可识别客户数据。
- 容器和故障测试只在授权服务器执行，不在开发者 Mac 运行 Docker/Colima。

## 4. 威胁模型与数据分级

### 4.1 优先威胁

1. 弱口令、泄露会话、越权接口或错误数据范围造成未授权查看/修改。
2. 密钥、Token、Cookie、银行账号或个人信息进入镜像、Git、日志、诊断包或错误响应。
3. 导出、恢复、升级、授权、删除等高风险动作无审计、可重放或可并发重复执行。
4. 依赖、基础镜像或发布物被篡改，版本、源码提交、镜像摘要和 SBOM 无法对应。
5. 数据库、磁盘、证书、时间、备份或第三方服务故障造成假成功、半写入或长期不可发现。
6. 异常断电、迁移中断或恢复错误造成库存、应收应付、资金、核销和附件不一致。
7. Copper 官方地址、遥测或许可证心跳成为离线运行的隐含依赖。
8. 日志或备份无限增长耗尽磁盘，反向损坏生产数据库和附件。

### 4.2 数据分级

| 级别 | 典型数据 | 最低保护要求 |
| --- | --- | --- |
| S0 公开 | 公开版本号、公开文档、公开依赖许可证 | 可公开，但发布来源和完整性需可验证 |
| S1 内部运营 | 非敏感健康状态、容量百分比、组件状态 | 仅授权用户可见，不含业务明细和秘密 |
| S2 业务敏感 | 客户/供应商、联系人、价格、订单、库存、附件 | 最小权限、数据范围、传输加密、导出审计、备份保护 |
| S3 财务/个人敏感 | 应收应付、收付款、核销、预收预付、银行账号、证件和联系方式 | S2 全部要求，并对展示/日志脱敏、危险动作加强认证与不可抵赖审计 |
| S4 秘密 | 密码、会话密钥、Cookie、数据库凭据、证书私钥、备份私钥/口令、API Token | 禁止进入镜像/Git/普通日志；最小文件权限、轮换、撤销、销毁和泄露处置 |

S2/S3 的完整业务数据可以按客户授权进入其自有备份和导出包；“日志不得记录”不等于“完整导出不得包含”。两者必须使用不同权限、格式、加密和审计边界。

## 5. 身份、会话、授权和数据范围

### 5.1 身份与会话

- 首次管理员一次性凭据必须强制改密并留下“已交付、已销毁”状态，公开默认密码永久禁止。
- 密码只保存强哈希；不得在审计、错误、日志、监控标签或通知中记录原文。
- 登录失败需要节流和可恢复锁定策略，不能用永久锁定制造客户无法自治。
- Cookie 至少采用 `Secure`、`HttpOnly` 和与同源部署相容的 `SameSite`；生产 TLS 终止下才允许登录验收通过。
- 登出、改密、管理员禁用、权限收回和安全事件处置必须能撤销相关会话。
- API 必须拒绝过期、伪造、重放或已撤销会话；写请求防重复提交不能只依赖 UI loading 状态。

### 5.2 授权

- 后端逐接口执行身份、角色、权限、数据范围和对象状态校验。
- 停用往来单位、已确认/已作废单据、已入账资金等业务状态仍按各自业务规则控制；安全权限不能绕过业务状态机。
- 财务、导出、恢复、升级、权限和危险删除采用显式高风险权限，不因拥有普通查询权限自动获得。
- 数据范围必须在完整查询、汇总、导出和附件下载中一致生效；禁止列表受限而导出/API 明细越权。

## 6. 审计事件合同

### 6.1 最小字段

每条安全/运维审计至少包含：事件 ID、事件类型、发生时间（含时区）、结果、主体用户/系统身份、会话或追踪 ID、来源 IP/客户端摘要、目标对象类型与稳定主键、动作、失败原因分类、版本和必要的前后状态摘要。

审计不得保存密码、Token、完整 Cookie、私钥、备份口令、完整证件号或完整银行账号。客户端可伪造的字段只能作为辅助信息，不能作为唯一责任证据。

### 6.2 强制审计矩阵

| 类别 | 必须记录的事件 | 业务结果所在位置 |
| --- | --- | --- |
| 身份 | 登录成功/失败、锁定/解锁、改密、登出、会话撤销、首次管理员交付/销毁 | 身份与会话状态 |
| 授权 | 角色、权限、数据范围、管理员启停的申请与结果 | 权限配置历史 |
| 数据自主 | 全量导出创建/完成/失败/下载/删除 | 导出任务、清单和文件摘要 |
| 备份恢复 | 备份、验证、下载/复制、恢复预检、恢复、切换、回滚、危险删除 | `copper-backup/v1` 和恢复状态机证据 |
| 发布升级 | 交付暂存、预检、准备、迁移、切换、回滚、丢弃、发布物验证 | M3 状态机与发布清单 |
| 高风险业务 | 资金、核销、库存调整、作废、冲正、权限控制的批量操作 | 原业务单据、流水、核销和审计历史 |
| 系统安全 | 秘密轮换、漏洞扫描、日志策略变更、外联/遥测变更 | 配置版本和安全证据 |
| 数据删除 | 卸载保留数据、危险删除确认、执行、失败和结果 | 删除清单与不可逆确认记录 |

审计只回答“谁以什么结果执行了动作”，不能用审计记录直接增减库存、结清应收、伪造收付款或覆盖核销关系。

## 7. 秘密、日志和供应链

### 7.1 秘密生命周期

- 生成：使用密码学安全随机源，禁止弱默认和多人共享固定秘密。
- 保存：root-only 文件或受支持的秘密挂载，默认权限最小化；不写环境样例的真实值。
- 使用：避免命令行参数和标准输出暴露；诊断命令只显示状态/指纹，不显示秘密。
- 交付：客户账户、备份恢复私钥和云侧凭据由客户持有，Copper 不成为唯一持有人。
- 轮换：明确旧秘密有效窗口、依赖更新顺序、失败回退和历史备份可恢复性。
- 撤销与销毁：保留动作证据但不保留秘密本体；泄露时可定位受影响版本、主机和时间段。

### 7.2 日志脱敏与保留

- 默认禁止记录请求/响应完整正文、Authorization、Cookie、密码字段、Token、数据库 DSN、密钥材料。
- 证件号、银行账号、手机号、邮箱和地址按用途最小展示；错误栈不得回显业务敏感数据。
- 应用、网关、数据库、审计和运维日志分别定义大小、轮转、保留时间、权限和清理优先级。
- 日志空间不得侵占数据库、附件和备份的危险保留量；进入危险阈值时优先阻止非必要大文件和高风险写入。

### 7.3 SBOM 与漏洞治理

- Web、Backend、Deploy 资产及基础镜像均生成机器可读 SBOM，并绑定产品版本、源码提交、镜像摘要和生成时间。
- 漏洞扫描必须可重复；结果包含组件、版本、严重度、可利用性判断、修复版本、处置人和例外到期日。
- 严重漏洞不得只以“扫描通过”关闭；必须修复、移除、证明不可达或形成有期限的风险接受。
- 安全修复仍遵守 M3 不可变发布、数据库迁移和客户自主升级规则；禁止移动已有 Tag 或覆盖镜像摘要。
- 建立 `SECURITY.md` 或等价安全报告入口，但不得要求报告者公开客户数据、秘密或可利用细节。

## 8. 外联与完全离线

所有主动外联必须进入机器可读清单：目标域名/地址、协议、方向、发送数据、用途、默认状态、关闭方法、失败影响和责任方。

默认规则：

- 核心采购、入库、库存、销售、出库、应收应付、收付款、核销和查询不访问 Copper 官方服务。
- 非必要遥测默认关闭，只有客户主动选择后才发送，并可随时关闭。
- 不存在远程许可证心跳、远程到期锁定或 Copper 停服后禁止登录的逻辑。
- 第三方短信、OCR、发票、地图、云打印、S3 和通知服务失败时，给出明确降级状态；不相关核心业务继续运行。
- DNS、NTP、证书续期和第三方服务属于外部依赖，应分别说明离线期间的可用窗口和恢复动作，不能把它们误称为 Copper 官方依赖。

M4-07 通过主机防火墙/DNS 拦截和连接观测验证：除验收明确允许的目标外无隐蔽外联；断网前已有有效证书时，核心业务在证书有效期内仍能使用现有 HTTPS，证书续期失败必须提前告警。

## 9. 健康、监控和告警合同

### 9.1 四层状态

| 层级 | 问题 | 典型证据 |
| --- | --- | --- |
| 存活 | 进程/容器是否运行 | 容器状态、进程退出码 |
| 就绪 | Web、Backend、MySQL 和必要依赖是否可服务 | 同源探测、Backend readiness、数据库读写探测 |
| 可写 | 当前是否允许安全提交业务写入 | 数据库、磁盘、迁移状态、停写锁和业务写保护 |
| 可恢复 | 最近成功备份是否已验证且客户具备恢复条件 | 备份摘要、验证时间、目标状态、恢复密钥实证 |

不得把下层成功冒充上层成功。例如容器运行不代表数据库可写，备份文件存在不代表校验通过或客户持有恢复私钥。

### 9.2 强制信号

- 应用：版本、启动时间、存活、就绪、可写、请求错误和必要依赖状态。
- 数据库：连接、MySQL 版本、Flyway 版本、只读/写入状态和容量风险；不暴露口令。
- 存储：数据库、附件、导出、备份、日志、临时目录的占用、剩余量、增长和阈值。
- 备份：最后成功、最后验证、连续失败、目标、大小、摘要和恢复密钥证明状态。
- 证书：域名、签发者、到期时间、续期状态和剩余天数；不读取/显示私钥。
- 时间：时区、系统时间、NTP 同步和偏差风险。

状态使用“正常、预警、严重、阻断”四级，每项给出发生时间、原因和下一步动作。通知失败必须留下本地状态，不能因第三方通知失败而丢失告警事实。

## 10. 容量、日志与写保护

- 容量阈值同时考虑绝对剩余空间和百分比，避免小盘/大盘单一百分比失真。
- 预警：允许业务继续但提示清理/扩容；严重：停止非必要大文件任务和新的导出/备份；阻断：禁止可能扩大损坏的业务写入。
- 数据库事务、附件上传、导出、备份和日志写入分别评估最坏临时空间，不能只看最终文件大小。
- 自动清理只作用于明确可再生且超过保留策略的文件；不得自动删除唯一成功备份、原始附件、业务数据或审计证据。
- 进入/退出写保护必须审计；恢复写入前重新检查数据库、磁盘和业务不变量。

## 11. RPO、RTO 与服务承诺

### 11.1 口径

- RPO（恢复点目标）：可接受的最大数据时间窗口，不等于“备份计划已配置”。
- RTO（恢复时间目标）：从确认故障到恢复约定服务能力的目标，不等于脚本运行耗时。
- 恢复完成：系统通过就绪、可写、可恢复检查，并复核经营财务不变量；仅启动容器不计完成。

### 11.2 决策边界

- M4-05 已基于 M2/M3/M4 真实演练，分别为自助部署、标准部署、安心维护和代运维制定可检查目标；权威运行合同由 `copper_deploy/config/operations-policy.json` 和 `copperctl operations status` 执行。
- 软件默认备份频率、客户实际调度、备份目标可用性和人工响应责任必须分开表述。
- 没有持续复制和对应运维能力时不得承诺零 RPO；没有 7×24 响应和容量保障时不得承诺即时 RTO。
- RPO/RTO、服务响应、超范围工作和第三方故障责任必须与价格及服务目录一致，并复算人工、安全响应和恢复演练成本。

M4-05 确定的工程基线为每日备份、24小时恢复点目标、30/48小时备份新鲜度预警/严重门槛、前提就绪后240分钟技术恢复目标和180天完整恢复演练新鲜度。自助与标准部署没有持续响应/RTO；安心维护为剩余额度内2个工作日响应；代运维为工作时段4个工作小时确认、前提就绪后8个工作小时恢复目标。上述均须 M4-07 复验，M7 才能依据成本和合同决定是否成为正式商业承诺，不构成7×24、零RPO或即时RTO。

## 12. 故障演练与恢复不变量

### 12.1 必测故障

| 故障 | 安全失败要求 | 恢复证据 |
| --- | --- | --- |
| 数据库不可用 | 写入明确失败，不返回假成功，不生成半业务结果 | 连接恢复、事务边界、重复提交检查、经营不变量 |
| 磁盘不足/耗尽 | 分级告警；危险时阻断大文件和业务写入 | 扩容/清理后重新检查并审计解除写保护 |
| 备份失败 | 不发布成功包、不更新成功时间、不删除旧成功备份 | 失败原因、本地告警、重试和新备份验证 |
| 证书过期/续期失败 | 提前告警，不自动降级为伪安全公网 HTTP | 修复 DNS/端口/时间并验证完整证书链和 Cookie |
| 系统时间异常 | 告警并阻断依赖可信时间的高风险流程 | NTP 恢复、时间偏差与审计顺序检查 |
| 异常断电/强制终止 | 不放行未知或半迁移状态 | 数据库恢复、Flyway、附件、队列/任务和业务不变量 |

### 12.2 经营财务不变量

每次恢复至少比对：

- Flyway 历史、业务表数量、外键/约束和发布版本。
- 商品、规格、单位、仓库、往来单位及其启停状态。
- 库存批次数量、库存流水和库存余额，禁止只比较某个列表页合计。
- 采购、入库、销售、出库、退货的单据数量、状态、数量与金额。
- 应收、应付、预收、预付、收款、付款、退款、调整、承兑和核销关系。
- 资金流水及账户余额；不得用伪造收付款或直接改订单金额制造“相等”。
- 附件清单、稳定路径、字节数和 SHA-256，以及历史审核快照引用。
- 审计事件的数量、时间顺序和关键高风险动作关联。

出现差异时不得自动覆盖原站或继续写入；保留证据并进入人工恢复流程。

### 12.3 M4-06 实施证据

2026-07-15，Ubuntu Server 24.04 LTS x86_64 隔离验收使用真实 MySQL 8.4 和正式 Compose 拓扑完成数据库断开、磁盘预警/严重/真实 ENOSPC、备份目标只读、过期证书、主机时间前跳 120 秒及三层容器 `SIGKILL` 等价异常断电。故障期间 API 和运维任务均明确成功、失败或未提交，没有用假回款、直接改订单金额或手工 SQL 制造一致。

可信时间状态目录由 root 控制并只读挂载给 Backend，真实应用写入探针被拒绝。恢复后 schema 5、90 张表、90 项 `CHECK TABLE`、40 项应用级引用检查、记录数、经营财务汇总、附件路径/字节/SHA-256 和审计证据完全一致；未提交事务没有出现，时间阻断期间财务写入没有产生账务行。36 条 root-only 事件形成 SHA-256 前向哈希链，最终证据清单 SHA-256 为 `9236bf1b1fd0006330e2861a7c92301a5f931af82309e48bff52a86e0fccc923`。

当前 schema 声明的数据库外键约束数量为 0，这是明确保留的结构风险。40 项应用级孤儿检查只证明本次固定范围和样本没有断裂关系，不替代数据库约束，也不覆盖未来新增关系；后续收紧必须使用新的正式 Flyway 迁移，先完成历史脏数据预检、性能和回滚验证。
