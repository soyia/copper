# M2 备份、恢复、导出与存储自主架构决策

> 决策状态：已接受；V1 全量已完成原验收，V2 增量链于 2026-07-21 完成工程实现及隔离 MySQL/附件恢复演练
> 决策日期：2026-07-13
> 适用仓库：`copper_web`、`copper_backend`、`copper_deploy`
> 对应里程碑：M2
> 格式版本：`copper-backup/v1` 全量基础包、`copper-backup/v2` 增量包、`copper-export/v1`

## 1. 决策目标

M2 要让客户真正拥有数据，而不是只增加一个“导出 Excel”按钮。必须同时交付两条互不替代的能力：

1. **灾难恢复备份**：可以在空白服务器恢复数据库、附件、必要配置和审计历史，并继续记账。
2. **人可读业务导出**：客户不运行 Copper、不使用 Copper 私有工具，也能读取完整业务数据、关系字段和原始附件。

存储空间由客户自己的服务器、磁盘、NAS或对象存储决定。Copper 不建立人为套餐容量，不以更换设备、云厂商或停止购买服务限制恢复和导出。

## 2. 核心决策

### 2.1 备份与业务导出必须分开

- `copper-backup/v1` 用于同版本灾难恢复，保留数据库类型、结构、精度、审计记录、附件原件和必要运行清单。
- `copper-export/v1` 用于长期可读和系统迁出，采用公开、通用格式，不要求导入后能够百分之百恢复 Copper 的内部运行状态。
- 列表页当前筛选结果、分页 API 返回或单张 Excel 均不得宣传为“完整备份”。
- 只有完整备份恢复验收和人可读导出验收都通过，才能对外承诺“数据可迁移、可恢复、可自由导出”。

### 2.2 M2 V1 采用短暂停写的一致性备份

Copper 同时保存 MySQL 业务记录和文件系统附件。仅使用数据库事务快照不能保证附件与数据库处于同一时间点，因此 V1 采用可解释、可复核的短暂停写方案：

1. `copperctl backup` 进入备份维护状态，停止新请求进入并等待进行中的上传和数据库事务结束。
2. 停止后端业务容器；MySQL、备份工具和只读诊断能力保持可用。
3. 记录数据库结构版本、应用版本、附件根目录和备份开始边界。
4. 导出 Copper 业务数据库，并复制该边界内的附件原件、允许清单内的配置和验证数据。
5. 在临时目录生成文件清单和 SHA-256；全部完成后再原子发布成功备份。
6. 无论成功或失败都执行受控恢复服务；数据库不健康时不得为了“恢复在线”强行开放业务写入。

该方案优先保证库存、应收应付、资金和附件的一致性，接受计划任务窗口内的短时不可写。V2 增量仍使用同一停写边界，只减少实际打包的数据量；存储快照和接近零停机仍属于后续优化，不能降低 V1/V2 的一致性门槛。

### 2.2.1 V2 每周全量、每日增量

- 每条链必须从可独立恢复的 `copper-backup/v1` 全量包开始；默认周日创建新全量基础包，周一至周六创建 `copper-backup/v2` 增量包。
- MySQL 固定启用 30 天保留的 `ROW` binary log 和 `FULL` row image。全量及每次增量都在 Web/Backend 停止、事务归零后轮换 binlog；全量 manifest 固化首个恢复截点，后续增量逐包固化起止截点，形成可离线复核的父/子边界。
- 增量包只包含父边界以后已经关闭的 binlog 文件；正在写入的新边界文件不进入当前包。恢复时先导入 v1 逻辑全量，再按父链使用同版本 `mysqlbinlog` 回放。
- 附件差异依据稳定路径、字节数与 SHA-256，记录新增、内容变化和删除墓碑。禁止只按文件修改日期或“本周目录”判断增量。
- `manifest.json` 和 `envelope.json` 同时记录 `baseBackupId`、`parentBackupId`、`chainSequence`；缺包、倒序、父 ID 不匹配或 binlog 边界不连续时失败关闭。
- 保留和删除以完整链为单位。任何仍被保留增量依赖的全量包及中间父包不得删除；断链和孤儿包不自动删除。
- 本机 root-only `chain-state.json` 仅用于续接下一增量，不是恢复所需的唯一事实。正式恢复只信任用户提供并逐包校验的加密包、父链和验证快照；链状态丢失时重建全量，不猜测续接位置。

### 2.3 备份包格式

正式扩展名为 `.copperbak`。它是未压缩的 POSIX pax tar 外层归档，可直接使用标准 `tar` 工具解包，不依赖 Copper 私有解包算法。推荐文件名：

```text
copper_<site-id>_<UTC时间>_<backup-id>.copperbak
```

外层至少包含：

```text
envelope.json
payload.tar.zst.age
checksums.sha256
README.txt
```

- `envelope.json` 只保存格式版本、备份 ID、站点匿名标识、生成时间、加密算法和密文校验值，不保存客户名称、业务数据或密钥。
- `payload.tar.zst.age` 是压缩后加密的完整载荷。V1 使用公开的 `age` 格式；生产备份默认必须加密。
- 备份服务器只保存客户指定的加密接收公钥。解密私钥或恢复口令由客户离线持有，不上传 Copper，也不得写入镜像、Git 仓库、普通配置文件或日志。
- 客户明确选择未加密备份时，命令必须给出高风险警告、二次确认并写入审计；上传 NAS 或对象存储的生产备份不得默认未加密。

解密后的载荷目录固定为：

```text
manifest.json
database/copper.sql.zst
attachments/
config/runtime-allowlist.json
verification/schema.json
verification/record-counts.json
verification/business-totals.json
verification/attachments.json
checksums.sha256
```

`manifest.json` 至少记录：

- `formatVersion`、`backupId`、`siteId`、创建时间、开始/结束边界和时区；
- Copper 发布版本、前端/后端镜像摘要、数据库类型和版本、数据库结构版本；
- 一致性方式、是否正常退出维护状态、数据库和附件文件数量及总字节数；
- 生成工具版本、压缩和加密算法、父备份 ID（V1 固定为空）；
- 配置允许清单、必要外部依赖声明和恢复兼容范围。

运行配置只按允许清单写入，默认不包含数据库口令、会话密钥、TLS 私钥和第三方密钥。恢复时重新生成可轮换密钥；确需保留的秘密只能进入已加密载荷中的独立秘密清单，并在恢复后提示轮换。

### 2.4 备份成功的原子边界

- 所有文件先写入同一目标文件系统的临时目录，成功校验后再原子改名为最终文件。
- 失败任务不得留下可被识别为“成功”的 `.copperbak`，不得更新“最后成功备份”时间，也不得触发保留策略删除旧成功备份。
- 自动清理只能删除已经完成且校验通过的完整备份链；必须始终保留最近一条完整链，并支持配置每日、每周、每月全量基础点数量。
- 上传对象存储时先使用临时对象名，上传后验证大小和 SHA-256，再发布最终对象和成功标记。
- 每次任务记录开始、结束、操作者/调度来源、目标、结果、字节数、校验结果和失败原因；日志不得记录密钥和业务内容。

### 2.5 恢复必须采用旁路暂存，禁止原地覆盖

标准恢复只允许指向空数据库和空数据根目录，流程如下：

1. 校验备份格式、外层和内层 SHA-256、解密能力、Copper/数据库版本兼容性。
2. 检查目标 CPU 架构、磁盘容量、目录权限、端口、镜像和预计恢复空间；可用空间至少覆盖备份解压、目标数据和安全余量。
3. 将数据库、附件和配置恢复到带恢复 ID 的暂存目录及新数据库，不修改当前可用实例。
4. 在隔离网络或非生产端口启动恢复实例，执行结构、记录数、关键业务余额、附件和审计校验。
5. 所有校验通过且操作者确认后，才切换正式数据指向；失败时删除或保留暂存现场用于诊断，原系统继续可用。

M2 V1 不提供“直接覆盖当前生产数据”的快捷恢复。必须保留恢复前备份、当前数据和暂存数据的明确边界，避免误操作把唯一可用副本一起破坏。

M2 只保证**同版本**或文档明确列出的兼容补丁版本恢复。跨数据库结构版本升级属于 M3，禁止在恢复流程中偷偷执行未审计升级。

### 2.6 恢复后的业务校验

恢复成功不能只以“容器启动”判断。必须自动比对备份清单中的：

- 数据库结构版本、基础表数量、每张业务表记录数和外键完整性；
- 库存数量与金额、应收、应付、预收预付、资金账户余额及核销关系汇总；
- 采购、入库、销售、出库、退货、收付款和审计记录数量；
- 附件数量、相对路径、字节数和 SHA-256；
- 管理员可登录、关键查询可读，并能在隔离验收副本完成一条受控测试业务链；验收后丢弃该副本或重新从备份恢复，禁止在正式恢复账套中删除测试业务来伪造回滚。

金额和数量必须使用数据库权威十进制字段计算并以字符串保存，不得使用前端显示值、浮点数或分页结果生成验收汇总。

### 2.7 人可读业务导出格式

正式扩展名为 `.zip`，格式版本为 `copper-export/v1`。目录至少包含：

```text
README.html
manifest.json
schema/
master-data/
purchasing/
inventory/
sales/
receivables-payables/
cash-and-settlement/
audit/
attachments/
checksums.sha256
```

- 每类实体提供 UTF-8 CSV；面向普通用户的核心汇总可额外提供 XLSX，但 CSV 和字段字典才是长期、开放的基线。
- 每张表都保留稳定业务主键、内部 ID、来源类型、来源 ID、状态、币种、原始精度、业务时间、入账时间、创建/修改人和审计时间。
- 金额、数量、单价、税额和汇率使用十进制字符串，不使用科学计数法；时间使用带时区的 ISO 8601，同时保留原业务日期列。
- 枚举同时导出机器值和中文说明；`schema/` 提供字段名、中文名、类型、精度、是否必填、关联实体和口径说明。
- 原始附件保持文件扩展名和字节内容，以稳定相对路径保存；附件清单关联业务类型、业务 ID、文件名、大小和 SHA-256。
- 导出查询在后端按权限和完整范围执行，禁止由前端翻页拼接；任务防重复提交、可查看进度、失败可重试，并进入审计日志。
- 客户可以导出全部数据，也可以按账套、业务日期和业务模块导出；任何筛选都必须写入 `manifest.json`，避免把局部导出误认为全量。

### 2.8 存储目标与容量规则

V1 定义统一备份目标接口，正式支持顺序为：

1. 客户服务器本地目录；
2. 已由操作系统稳定挂载的 NAS 目录（NFS/SMB 由客户环境负责挂载与权限）；
3. S3 兼容对象存储。

同一备份包在不同目标上的字节内容和 SHA-256 必须一致。存储适配器只负责写入、读取、列举、校验和删除，不得改变备份内部格式。

界面和 `copperctl` 展示数据库、附件、备份占用量、目标剩余空间、最近成功/失败时间和下一次计划，不展示 Copper 人为“套餐空间”。对象存储无法提供可靠剩余容量时必须显示“由存储供应商配额决定”，不能伪造无限容量。

空间不足按风险分级：

- 预警：提醒清理或扩容，但核心业务继续运行；
- 严重：禁止启动可能产生大文件的备份、导出和批量上传；
- 危险：当数据库自身继续写入可能损坏时，进入受控只读或停止写入，并给出恢复步骤。

## 3. 仓库责任边界

| 仓库 | M2 责任 |
| --- | --- |
| `copper_deploy` | `copperctl backup/restore`、备份包组装与加密、保留策略、存储适配器、旁路恢复、运维诊断和真实环境验收脚本 |
| `copper_backend` | 权威业务导出查询、字段字典、权限和审计、完整余额校验、附件清单和存储容量/备份状态 API |
| `copper_web` | 备份状态、空间状态、导出任务与恢复风险的信息展示；不在浏览器拼接全量数据，不让前端成为灾难恢复依赖 |

跨仓库契约先写入版本化清单和测试样例，再分别实现。任何单仓库 PR 都必须说明对另外两端的兼容影响。

## 4. M2 实施顺序

1. **M2-01**：冻结本决策、`copper-backup/v1` 和 `copper-export/v1` 契约。
2. **M2-02**：实现一致性整站备份、原子发布、校验和保留策略。
3. **M2-03**：实现旁路恢复、自动验证和失败不覆盖。
4. **M2-04**：实现完整、人可读、可审计的业务导出。
5. **M2-05**：实现本地、NAS和 S3 兼容存储目标与容量治理。
6. **M2-06**：收口客户持钥、自动调度、告警和密钥销毁/轮换机制。
7. **M2-07**：完成空白服务器恢复、跨环境迁移、导出可读性和 M2 退出验收。

M2-02 和 M2-04 可在 M2-01 合并后并行设计，但 M2-07 必须等待 M2-02 至 M2-06 全部完成。

## 5. M2-01 验收结论

- 已明确灾难恢复备份和人可读导出的不同目的，禁止互相冒充。
- 已冻结 V1 备份格式、加密与客户持钥边界、短暂停写一致性策略和失败原子性。
- 已冻结旁路恢复、恢复前检查、恢复后财务/库存/附件校验和同版本兼容范围。
- 已冻结开放导出格式、十进制精度、关系字段、附件目录、权限和审计要求。
- 已明确三个仓库的责任边界、七个实施 Issue 和最终退出依赖。

本决策通过不等于 M2 已完成。只有 M2-07 在真实空白服务器上证明可恢复、可继续记账、关键余额一致、附件一致且导出可独立读取，路线图 M2 才能勾选完成。

## 6. 本阶段不承诺的事项

- 不承诺零停机、实时连续备份、跨地域自动故障切换和任意时间点恢复；这些能力必须在真实成本和客户需求明确后单独排期。
- 不承诺任意数据库结构版本之间直接恢复；跨版本迁移属于 M3。
- 不把 NAS 挂载、对象存储账号、云厂商费用和客户网络质量包装成 Copper 软件免费提供的资源。
- 不以 M2 备份替代客户的异地副本、硬件容灾和定期恢复演练责任。
