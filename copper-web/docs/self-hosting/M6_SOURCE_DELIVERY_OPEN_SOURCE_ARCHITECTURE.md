# M6 客户源码交付与公开开源准备架构

> 状态：M6-01 已完成（Web PR #62）；M6-02/M6-03 可开始，工程和法律门槛尚未全部实施
> 决策日期：2026-07-16
> 总跟踪：[`soyia/copper_web#57`](https://github.com/soyia/copper_web/issues/57)
> 架构任务：[`soyia/copper_web#58`](https://github.com/soyia/copper_web/issues/58)
> 前置条件：M1 至 M4 已完成；不等待延期的 M5-07

本文冻结 Copper 在公开开源前向正式部署客户交付源码，以及将来准备公开仓库时必须遵守的产品、工程、安全、版权和发布边界。本文是 M6 的工程架构基线，不是最终开源许可证、商标许可或法律意见；未经 M6-05 专业法律复核，不得创建最终 `LICENSE`、开放外部贡献或宣称 Copper 已正式开源。

## 1. 目标与不可变原则

1. **完整自主**：客户不因 Copper 停止服务而失去运行、修复、构建、迁移、备份和灾难恢复能力。
2. **单一产品**：客户源码交付版、未来公开版和官方部署版使用同一套核心业务源码，不按用户数、仓库数、商品数、单据数或人工存储配额拆分功能版本。
3. **精确对应**：源码交付必须与客户实际运行版本、数据库迁移、镜像和发布清单建立机器可核对的唯一对应关系。
4. **完整核心**：采购、入库、库存、销售、出库、应收应付、收付款、对账、导出、备份恢复和升级能力不得以“内部服务”为名从交付或公开核心中移除。
5. **失败关闭**：秘密、客户数据、权利不明资产、许可证冲突、不可复现构建或法律门槛未通过时，阻止源码交付候选或公开发布，不得以人工口头确认绕过。
6. **权威单一**：GitHub `origin/main` 是当前唯一集成和交付权威源。M6 不读取、写入或同步 Gitee；未来增加任何镜像必须由产品负责人另行明确授权并证明不会形成产品分叉。
7. **专业复核**：工程扫描不能替代知识产权律师对开源许可证、双授权、贡献授权、商标和第三方权利的专业判断。

## 2. M6 边界

### 2.1 纳入 M6 的内容

- `soyia/copper_web`：完整前端、用户业务流程、打印/导出界面、前端构建和依赖锁。
- `soyia/copper_backend`：完整业务规则、数据模型、权限、审计、金额和数量计算、数据库迁移及后端构建。
- `soyia/copper_deploy`：正式安装、升级、回滚、备份、恢复、导出、监控、离线交付和发布清单能力。
- 三仓当前树和 Git 历史中的秘密、客户数据、个人信息和受限资产审计。
- 第三方代码、依赖、字体、图标、图片、文案、商品目录、示例数据和采集内容的来源与再发布权审计。
- 客户源码交付包、离线可复现构建、SBOM、许可证清单、治理文件和公开仓库演练。

### 2.2 可以保留为厂商内部资产的内容

- Copper 自身的客户服务工单、排班、服务计费、合同管理和内部经营系统。
- 官方签名私钥、制品仓库凭据、云账号、CI/CD 运行秘密及未公开的安全响应材料。
- 受客户保密义务约束、只属于特定客户且不构成通用核心产品的迁移映射、数据和定制代码；其交付按客户合同单独处理。

上述内部资产不得被核心运行时强制依赖。客户停止购买服务后，完整核心系统仍须能够离线运行、备份恢复、升级到其有权取得的版本并自由导出数据。

### 2.3 明确排除的内容

- 任何生产或测试密钥、令牌、密码、Cookie、证书私钥、SSH 私钥和正式签名凭据。
- 客户数据库、备份、附件、导出文件、个人信息、真实业务日志、内部截图和未脱敏验收证据。
- 权属不清、许可证不兼容、未经许可采集或不能合法再发布的第三方资产。
- 仅用于维护者本机的临时文件、缓存、运行目录、编辑器状态和内部访问配置。

## 3. 核心系统与功能一致性

| 能力 | 客户源码交付 | 未来公开核心 | 厂商内部服务可替代 |
| --- | --- | --- | --- |
| 前端和后端核心业务 | 必须完整 | 必须完整 | 否 |
| 数据库初始化与不可变迁移 | 必须完整 | 必须完整 | 否 |
| 安装、升级、回滚 | 必须完整 | 必须完整 | 否 |
| 完整导出、备份、恢复 | 必须完整 | 必须完整 | 否 |
| 本地监控和安全状态 | 必须完整 | 必须完整 | 否 |
| 官方签名私钥和 CI 凭据 | 禁止交付 | 禁止公开 | 是 |
| 厂商工单、计费和代运维控制面 | 不要求 | 不要求 | 是 |

官方托管、专业支持、定制、迁移和品牌认证可以收费，但不得通过隐藏核心代码、远程许可证心跳、遥测依赖、远程停用开关或数据锁定制造功能差异。

## 4. 精确版本源码交付合同

每个源码交付包必须包含机器可读的 `copper-source-delivery/v1` 清单。清单至少绑定：

| 分组 | 必填内容 |
| --- | --- |
| 产品 | 产品版本、发布日期、发布清单版本与 SHA-256 |
| 源码 | 三仓 GitHub URL、精确提交 SHA、标签、源码树/归档 SHA-256 |
| 数据库 | schema 版本、基线、完整迁移集合及集合 SHA-256 |
| 运行工件 | Web、Backend、MySQL 和部署组件的不可变镜像摘要 |
| 构建 | Node/pnpm、JDK/Maven、Docker/Compose 等工具链版本和构建命令 |
| 依赖 | 锁文件、离线依赖索引/介质、基础镜像和第三方许可证清单 |
| 安全 | SBOM、秘密扫描、客户数据扫描和已批准例外的证据摘要 |
| 文档 | 构建、安装、升级、回滚、备份、恢复、导出和故障排查说明 |
| 验真 | 文件清单、每文件 SHA-256、清单签名方式及客户离线校验命令 |

规则：

- 只写版本号、分支名或可变镜像标签不构成有效绑定。
- 源码快照必须来自已经合入三仓 `main` 的精确提交；不得从开发者脏工作区临时打包。
- 客户包默认交付经过 M6-02 审计的精确源码树和必要提交元数据，不默认暴露未经完整审计的全部历史。
- 离线交付必须包含构建/运行所需的正式离线依赖和镜像，或提供经过空白断网验证、内容摘要固定的等价介质。
- 归档应使用固定文件顺序、权限、换行和可控时间戳等可复现规则；M6-04 冻结具体格式和 `SOURCE_DATE_EPOCH` 策略。

## 5. 客户源码包内容

### 5.1 必须包含

- 三仓完整核心源码及锁定依赖文件。
- 数据库初始化基线和从支持起点到交付版本的全部不可变迁移。
- 正式安装、升级、回滚、备份、恢复、导出、监控和卸载脚本。
- 离线依赖/镜像介质、正式构建命令、支持平台和资源基线。
- 发布说明、已知限制、SBOM、第三方许可证清单、校验清单和验真说明。
- 与客户当前许可相符的源码使用条款和已签署交接单。

### 5.2 客户必须取得的自主权基线

在正式公开前，中国境内低风险试运营继续适用 `CHINA_TRIAL_TERMS.md`；源码条款至少保证客户永久内部运行、修改、构建、备份、灾难恢复和委托受保密义务服务商维护的权利，不设置用户数、仓库数、商品数、单据数和人工存储配额。

公开再发布、改名销售、公共 SaaS、OEM、商业再许可和 Copper 商标使用不由 M6-01 直接授权，必须按 M6-05 的最终许可证、商标和商业合同处理。

### 5.3 交付过程

1. 从三仓已合入 `main` 的精确提交生成候选，禁止从本地未评审提交生成。
2. 生成源码、迁移、镜像、依赖、SBOM、许可证和文件校验清单。
3. 执行 M6-02/M6-03 的秘密、客户数据、隐私、版权和许可证门槛。
4. 在独立空白环境完成构建、部署、核心业务、导出、备份和旁路恢复。
5. 对最终清单签名并交付；客户在自己控制的设备上离线复核 SHA-256 和签名。
6. 双方签署源码与凭据交接记录；Copper 不保管客户唯一恢复材料，不要求客户依赖 Copper 才能验真。

## 6. 安全、历史与隐私审计

M6-02 的工程门禁、首次脱敏三仓扫描结果和仍未完成的阻塞处置见 `M6_02_SECURITY_PRIVACY_AUDIT.md`。首次 baseline 只用于阻止 PR 新增泄漏，不构成误报批准或严格发布通过。

M6-02 必须同时扫描三仓当前树和完整可达历史，至少覆盖：

- 通用秘密模式、云/数据库/SSH/证书凭据和高熵字符串。
- 数据库备份、附件、导出、日志、截图、客户名称、联系人和个人信息。
- `.env`、运行配置、CI 日志、Release 资产、标签和曾经删除的历史对象。

发现项必须逐条归类为移除并轮换、历史重写、授权保留或有证据的误报。历史重写会破坏既有提交和克隆的身份，必须先形成影响清单、备份、旧标签/Release 处置、协作切换和回退方案，禁止自动或静默执行。

扫描报告只保存脱敏路径、规则、分类、处置和摘要，不能把命中的秘密或个人信息再次写入证据。PR 和 Release 门槛出现新泄漏时必须失败关闭。

## 7. 第三方权利、许可证和 SBOM

M6-03 必须为前端、后端、部署、构建工具、基础镜像和内容资产建立可追溯台账。每项至少记录名称、版本/摘要、来源、作者/权利人、许可证、许可证文本位置、使用方式、再发布结论、归属/NOTICE 要求和复核状态。

字体、图标、图片、文案、标准文件、示例数据、商品目录和网站采集内容不能只因“网上可见”就视为可公开再发布。权利不明确时应替换、自行创作、取得书面授权或从公开候选中移除；不得用免责声明代替权利来源。

截至 2026-07-16，Web 仓库中的宏泰官网抓取快照及外部图片已从当前树移除，对应抓取脚本和包命令也一并取消。青岛宏泰官网 URL 只保留为 15 类商品范围的业务参考，不复制其网页、图片或文案。仓库外保留的内部研究副本不属于客户源码包、镜像、Release 或公开仓库，也不代表已取得再发布授权。

初始清理阶段只移除了当前树；随后经产品负责人授权，三仓普通 GitHub 历史已重置为单根 `main`，Deploy 旧标签和 Release 入口已删除。GitHub 托管历史 PR refs、页面与缓存不随普通 Git 改写删除，仍由 M6-02 的影响评估、私有回退、Support 清理申请和复核处理；不能因普通 `main` 已通过就宣称全平台历史审计完成。生产契约会阻止该抓取目录和同步脚本重新进入交付候选。

SBOM 和人可读许可证清单必须绑定产品版本、三仓提交和镜像摘要，并随客户源码包及未来公开 Release 一起发布。工程扫描结果仍须进入 M6-05 法律复核。

## 8. 许可证、贡献与商标决策门槛

M6-01 只冻结决策流程，不选择最终许可证。M6-05 必须由知识产权律师结合全部依赖、既有代码权属和商业模式复核：

- AGPLv3 是否适合 Copper 的网络使用和再分发目标。
- 商业双授权是否具备完整版权链，以及外部贡献采用 CLA、DCO、版权转让或其他方式。
- 第三方依赖能否与候选许可证和离线再发布方式兼容。
- 既有客户私有源码条款如何与未来公开许可证衔接。
- Copper 名称、Logo、域名、官方认证、分叉命名和商业支持标识的商标边界。
- 无担保、责任限制、安全更新、第三方组件和商业支持条款。

在复核完成并形成证据前：

- 不创建或复制“暂定”的最终 `LICENSE`。
- 不把仓库设为公开，不接受外部贡献，不宣传“已开源”。
- 不签署公共 SaaS、OEM、跨境或其他超出既有中国低风险试运营范围的高风险源码授权。

内部演练阶段的事实、待决策问题、证据清单和律师签署栏见 [M6-05 法律复核材料包](M6_05_LEGAL_REVIEW_PACKET.md)。该材料包不构成法律结论，不能替代本节门槛；在 M6-02、M6-03 和律师书面结论全部通过前，正式对外状态必须保持 `FORMAL_RELEASE_BLOCKED`。

## 9. GitHub 权威源与未来镜像

- 三仓 GitHub `origin/main` 是代码、标签、Release 和交付清单的唯一权威来源。
- GitHub Issue/PR 是普通问题和贡献的唯一权威入口；安全漏洞使用 `SECURITY.md` 指向的 GitHub 私密报告入口。
- 所有普通变更通过分支、PR、评审和合并进入 `main`，禁止把未评审分支或本地提交装入客户源码包。
- 当前 M6 工作不访问、不修改、不配置 Gitee。
- 若未来确有国内镜像需求，必须另行批准只读单向镜像、同步延迟、标签/Release 校验、显著权威源公告和失配停发机制；镜像不得独立接受 PR、Issue 或发布不同版本。

## 12. M6 总退出条件

只有以下条件全部满足，M6 才能关闭并允许进入 M7 正式发布：

- 三仓发布候选通过当前树、完整历史、秘密、客户数据和个人信息审计。
- 第三方代码和内容具有可追溯权利，许可证清单、NOTICE 输入和 SBOM 完整。
- 最终许可证、贡献机制和商标规则取得专业法律复核并落实到治理文件。
