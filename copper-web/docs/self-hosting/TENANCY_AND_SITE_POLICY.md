# 经营主体、站点与账套隔离规则

> 状态：内部产品规则
> 对应任务：GitHub `soyia/copper_web#1`
> 适用范围：Copper 本地部署、客户云部署、备份、恢复、迁移和后续跨站点能力

## 1. 核心结论

Copper 默认采用：

> 一个独立经营主体 = 一个 Copper 站点 = 一个独立业务数据库。

这里的“独立经营主体”是需要独立回答库存、应收应付、资金、业务编号、审计责任和经营结果的主体，不仅按是否领取营业执照机械判断。

## 2. 概念定义

| 概念 | 定义 | 隔离要求 |
| --- | --- | --- |
| 经营主体 | 独立承担采购、销售、库存、往来和资金责任的业务主体 | 默认独立站点和数据库 |
| Copper站点 | 一套可独立启动、备份、恢复和升级的 Copper 生产实例 | 不与其他主体共用业务表 |
| 业务账簿 | 同一主体内按期间连续记录业务数据的逻辑账 | 不通过新建账簿切断历史追溯 |
| 部门/直营网点 | 同一主体下的组织或经营单元 | 可在同一站点内按权限和数据范围管理 |
| 仓库 | 同一主体下的库存地点 | 在同一站点内独立核算库存，不等于独立经营主体 |
| 生产环境 | 承载真实业务数据的一套运行环境 | 部署、维护和代运维按环境核算服务 |

## 3. 可以放在同一站点的场景

- 同一经营主体下的多个部门、员工和权限角色。
- 同一经营主体下的多个仓库、直营网点和销售区域。
- 同一经营主体连续多个会计或经营年度的历史数据。
- 同一经营主体同时具有客户和供应商往来角色的合作方。
- 同一经营主体内部需要统一对账、统一资金账户和统一库存追溯的业务。

不得为了“年度结转”随意新建空账套并切断原业务单据。年度查询应通过业务日期、期间和结账规则实现，历史单据继续可追溯。

## 4. 必须使用独立站点的场景

- 两个独立公司、个体工商户或其他需要独立承担经营责任的主体。
- 即使属于同一控制人，但库存、资金、应收应付或发票主体必须独立的业务。
- 需要独立数据库管理员、独立备份密钥或独立数据交付边界的客户。
- 数据依法、依合同或依内部控制不得互相访问的主体。

禁止使用 `company_id` 等普通筛选字段，把原本应物理隔离的独立主体简单塞进同一数据库后宣传“无限账套”。这会使越权查询、编号冲突、备份拆分、恢复、资金对账和审计责任复杂化。

## 5. 多站点收费原则

- Copper 软件核心功能不按站点、账套或用户收费。
- 客户自助创建多个站点，不产生软件功能费。
- Copper 提供人工部署、迁移、升级、维护或代运维时，按实际生产环境收费，因为每个环境都需要独立配置、备份、恢复验证和安全责任。
- 测试/演练环境是否收费由具体服务目录决定，不得通过限制软件功能强制收费。

## 6. 数据和编号规则

- 合作方编号、商品编号、采购/销售/出入库单号在站点内唯一。
- 库存余额、应收、应付、资金和预收预付只在本经营主体内汇总。
- 每个站点独立备份、恢复、导出和校验，不允许恢复一个主体时覆盖另一个主体。
- 跨主体汇总只能通过明确的只读汇总、报表或数据仓库实现，不得直接合并业务流水冒充统一账。
- 跨主体调货、代收代付和往来必须在双方站点形成各自有来源、可对账的业务记录；不得直接改另一站点库存或资金。

## 7. 当前架构结论

当前 Copper 后端业务表没有统一 `tenant_id`/`organization_id` 多租户边界，数据库天然更接近单站点、单经营主体模型。M1 应沿用单站点部署，而不是在部署阶段顺带引入高风险多租户改造。

未来如确有集团多主体统一登录需求，应单独立项设计身份中心、站点切换、跨站点权限、合并报表和审计边界，不能改变本规则中的业务数据隔离原则。

## 8. 验收结论

- [x] 默认一经营主体一站点/数据库。
- [x] 同主体多部门、仓库、直营网点放在同一站点。
- [x] 独立主体使用独立站点和数据库。
- [x] 软件功能不按站点收费，人工服务按生产环境核算。
- [x] 跨站点汇总不得破坏原始库存、往来、资金和审计记录。
