# Copper M1 标准生产部署基线与架构决策

> 决策状态：已生效；M1 内部交付基线已通过，中国大陆公网与 Chrome/Edge 客户端访问等待域名备案后补验
> 决策日期：2026-07-13
> 关联 Issue：<https://github.com/soyia/copper_web/issues/7>
> 适用范围：首个中国境内 Linux/客户云正式部署基线

## 1. 决策结论

Copper M1 只支持一个经过完整验收的标准生产基线，不同时承诺多种 Linux、CPU 架构、数据库、容器编排或本地/NAS 环境。首个基线采用单站点、单经营主体、单数据库的 Compose 部署；客户拥有服务器、数据库、附件、配置、备份和密钥的最终控制权。

M1 的完成含义是“发布包可以在标准云服务器上重复安装并稳定重启”，不等于 M2 的完整可迁移备份恢复，也不等于 M3 的可控升级和失败回滚。

## 2. 首个支持矩阵

| 项目 | M1 正式基线 | 说明 |
| --- | --- | --- |
| 服务器系统 | Ubuntu Server 24.04 LTS | 仅支持 64 位官方 Ubuntu Server；衍生发行版不进入 M1 承诺。 |
| CPU 架构 | x86_64/amd64 | arm64 在独立真实验收完成前不列为正式支持。 |
| 最低资源 | 2 vCPU、4 GiB 内存、50 GiB SSD | 只用于低并发试点；安装前检查可用磁盘。 |
| 推荐资源 | 4 vCPU、8 GiB 内存、100 GiB SSD | 磁盘容量由客户业务量决定，Copper 不设置软件配额。 |
| 容器运行时 | Docker Engine 29.x | 使用 Docker 官方 apt 仓库安装；M1-07 记录实际补丁版本。 |
| 编排工具 | Docker Compose Plugin 5.x | 使用 `docker compose`，不支持旧 `docker-compose` Python 程序。 |
| 数据库 | MySQL 8.4.x LTS | 数据目录必须使用持久卷；数据库端口不发布到公网。 |
| 后端运行时 | Java 17 | 构建镜像和运行镜像分别锁定，并记录镜像摘要。 |
| 浏览器 | Chrome、Edge、Firefox 最近两个稳定大版本；Safari 当前与前一稳定大版本 | 中国大陆 M1-07 经负责人确认先完成本机 HTTPS 与 API 业务链；公网 Chrome/Edge 核心链路必须在域名备案接入后补验。 |
| 时区 | Asia/Shanghai | 宿主机、JVM、MySQL 和业务显示口径保持一致。 |

支持矩阵只描述首个验收组合。其他云厂商可以使用，只要提供同等的标准 Ubuntu 云主机；云厂商品牌不是软件版本差异。

## 3. 正式服务拓扑

```text
Internet
   |
   | 80/443
   v
Copper Web Gateway (Caddy 2 + Vue 静态文件)
   |
   | /api，保留原始路径
   v
Copper Backend :8191（仅内部网络）
   |                         |
   | JDBC                    | 文件读写
   v                         v
MySQL :3306              附件持久卷
（仅内部网络）
```

### 3.1 网络和端口

- 宿主机只允许网关发布 `80/tcp` 和 `443/tcp`。
- Backend `8191` 和 MySQL `3306` 只在 Compose 内部网络可达，不映射宿主机端口。
- 网关把 `/api` 原样转发到 Backend；后端已经使用 `/api` context path，禁止再次拼接或剥离造成 `/api/api`。
- Vue 使用 History 路由；非 `/api` 且不存在的静态路径回退到 `index.html`。
- 有客户自有负载均衡或反向代理时，可以由外部终止 TLS，但内部网关路由规则和健康检查保持不变。

### 3.2 TLS 和域名

- 标准模式由 Caddy 自动申请和续期公开域名证书。
- 只有 IP、内网域名或客户已有证书时，必须选择明确的 HTTP/自有证书模式，不允许安装脚本静默降级。
- 域名、证书和云账号始终归客户持有；Copper 代运维也不得成为唯一控制方。

### 3.3 持久数据边界

| 数据 | 建议挂载点 | 删除规则 |
| --- | --- | --- |
| MySQL 数据 | `/var/lib/copper/mysql` | 普通停止、重启、卸载均保留。 |
| 原始附件 | `/var/lib/copper/files` | 与数据库作为同一站点资产管理。 |
| 站点配置 | `/etc/copper` | 权限最小化；不得提交 Git。 |
| 基础备份 | `/var/lib/copper/backups` | M1 仅支持同版本停机式基础备份。 |

应用日志优先写标准输出并由 Docker 管理轮转，不把无限增长的日志写进业务数据卷。永久删除上述目录必须使用独立危险命令、显示目标站点标识并二次确认。

## 4. 部署资产归属

| 仓库 | 权威资产 |
| --- | --- |
| `soyia/copper_web` | 前端源码、前端 Dockerfile、静态站点与同源 `/api` 配置、跨仓库路线图。 |
| `soyia/copper_backend` | 后端源码、后端 Dockerfile、数据库 V1 基线、V2 及后续不可变迁移、后端健康检查。 |
| `soyia/copper_deploy` | Compose、`copperctl`、Caddy 模板、配置示例、安装/排错文档、版本兼容清单和发布包。 |

`copper_deploy` 是唯一正式安装入口。前后端仓库不得各自复制一套 Compose 或安装脚本；开发环境脚本不能作为客户交付资产。

## 5. 发布版本对应规则

每个 Copper 发布版本必须形成一个不可变发布清单，至少记录：

- Copper 产品版本，例如 `1.0.0`。
- `copper-web` Git 提交、镜像标签和镜像摘要。
- `copper-backend` Git 提交、镜像标签和镜像摘要。
- 数据库结构版本，例如 `V1`。
- `copper-deploy` Git 提交和发布包校验值。
- 已验收的 Ubuntu、Docker、Compose 和 MySQL 版本。

安装时使用镜像摘要或不可变发布标签，禁止依赖会漂移的 `latest`。一个站点只能运行发布清单中经过配套验证的前端、后端和数据库版本。

## 6. 首发数据库 V1 决策

### 6.1 权威来源

本次是 Copper 首个正式数据库版本。历史开发 SQL 不再被重新排序、补编号或纳入首发迁移链；M1-05 必须全部移除现有历史 SQL，并从验收通过的真实 `copper_v2` 数据库生成唯一 V1 基线。

2026-07-13 的切换前只读结构快照记录如下：

| 项目 | 快照值 |
| --- | --- |
| 当前数据库版本 | MySQL 8.0.42 |
| 数据库名 | `copper_v2` |
| 基础表 | 87 |
| 视图、触发器、存储过程、事件 | 均为 0 |
| 当前 `c_` 前缀基础表 | 87 |
| 规范化结构导出 SHA-256 | `f4cec8d6f0c6cf8b3364c9e25c52dc8e937ce38a8acb7b6f731d334b390f7d94` |

在完成桌面全库备份并由用户停止 8191 后，87 张表已经通过单条原子 `RENAME TABLE` 切换为当前 Backend 使用的无 `c_` 前缀表名。切换后仍为 87 张基础表，`c_` 前缀表为 0，断裂外键目标为 0，87 张表的 `mysqlcheck` 均为 `OK`，规范化结构导出 SHA-256 为 `ccd5250750325f5b5c78b9a9f9a79281a3de13a450e44754f792e66e13639490`。

本次切换只完成开发数据库表名与代码对齐，不等于最终 V1 已验收。8191 在隔离数据库完成无前缀 V1、空库初始化和核心业务回归前保持停止。当前数据库来自 MySQL 8.0.42，而目标运行时是 MySQL 8.4 LTS，只有 M1-05 验证全部通过后才能宣称兼容。

### 6.2 V1 生成规则

- 结构导出必须在明确的冻结窗口执行，并记录数据库版本、对象清单、命令参数和 SHA-256。
- 最终 V1 的表名必须与当前无 `c_` 前缀 Backend 代码和已切换开发数据库一致；切换前 `c_` 前缀快照不得冒充最终 V1。
- V1 只包含数据库结构和经过逐表审核的系统必要种子数据。
- 禁止带入客户、供应商、联系人、订单、库存、应收应付、资金、账号口令、会话和附件等业务或敏感数据。
- 必要种子数据使用白名单，不得用“导出全部数据后再删除”的方式生成。
- V1 在首发前允许重新生成；一旦 `1.0.0` 发布即永久只读。
- `1.0.0` 之后从 V2 开始使用版本化迁移，已发布迁移不得覆盖修改。

## 7. 安全和初始化基线

- 安装时生成随机数据库应用账号密码；不允许 `root/123456`、空密码或公共默认密码。
- 数据库 root 凭据只用于数据库初始化，Backend 使用最小必要权限的应用账号。
- 首个管理员通过一次性初始化凭据创建；成功后立即销毁引导凭据并强制首次改密。
- 密钥只保存在客户服务器的受限配置目录、Docker Secret 或其他等效机制中，不写入镜像、日志或 Git。
- 健康接口只返回存活/就绪状态，不公开配置、环境变量、数据库地址或版本明细。
- CORS 仅保留本地开发配置；正式环境依赖同源访问。

## 8. 健康检查和启动顺序

1. MySQL 通过自身健康检查并可接受连接。
2. Backend 完成 V1 初始化或后续迁移、配置校验和一次性管理员引导准备。
3. Backend 存活检查只判断进程内部状态；就绪检查必须保证可以处理业务请求。
4. 网关在 Backend 就绪前可以提供静态维护页，但不得把业务流量转发到未就绪后端。
5. `copperctl doctor` 汇总端口、容器、数据库、磁盘、目录权限、证书和健康状态，并给出下一步处理建议。

## 9. M1、M2 和 M3 的范围边界

- M1：安装、启动、停止、重启、状态、日志、诊断、管理员初始化、默认保留数据的卸载，以及同版本停机式基础备份/恢复。
- M2：数据库与附件一致时间点、版本化备份包、校验、加密、自动保留、NAS/对象存储、跨服务器恢复和人可读完整导出。
- M3：跨版本升级、升级前检查、自动迁移、失败回滚、离线发布包和发布签名。

M1 文档和界面不得提前使用“完整恢复”“无损迁移”“安全升级”等尚未通过后续里程碑验收的表述。

## 10. 实施顺序和退出证据

1. M1-01 合并本决策并冻结基线。
2. 并行实施 M1-02、M1-03、M1-05。
3. 镜像和数据库基线完成后实施 M1-04。
4. 编排稳定后实施 M1-06。
5. 最后在全新标准云服务器执行 M1-07。

M1-01 合并只代表架构决策完成，不代表 Copper 已经可以一键部署。M1-07 已完成空白服务器离线安装、业务链路、重启持久性和错误恢复；M1 标记为内部交付基线完成。中国大陆公网与 Chrome/Edge 客户端访问仍须在域名备案接入后补验，补验前不得宣称公网正式交付已通过。
