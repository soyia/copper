# M5 本地设备、局域网与 NAS 标准化交付架构

> 状态：架构基线（M5-01）
> 生效日期：2026-07-15
> 适用版本：`0.3.0-rc.4` 后续 M5 候选版本
> 权威路线图：`docs/SELF_HOSTING_AND_DATA_CONTROL_ROADMAP.md`
> 总跟踪 Issue：<https://github.com/soyia/copper_web/issues/41>
> M5-01 Issue：<https://github.com/soyia/copper_web/issues/42>

本文冻结 M5 的支持分级、候选平台顺序、网络、TLS、存储、外设、休眠和服务价格边界。它是 M5-02 至 M5-07 的实施合同，不代表 Windows、macOS、NAS 或任意本地设备已经正式支持。只有真实设备完成全新安装、重启、升级、备份、恢复、迁移、局域网和外设验收后，才能进入对外兼容清单。

> 2026-07-16 执行范围决定：当前只完成两包实体体验验收——现有 Mac 作为主要操作终端并以手机作为独立第二终端/客户端休眠观察端；借用实体 A4 打印机完成实际打印。独立 Ubuntu 本地主机、Windows 宿主 Ubuntu VM、HID 扫码枪、针式打印机、主机休眠与 LAN 地址变化，以及真实外接盘、远程 NAS、设备 B 和客户离线恢复私钥交接均延期。两包通过后可以开始 M6，因为 M6 只依赖 M1 至 M4；这不等于 M5-07 通过，也不产生本地 `Certified` 平台。延期项最迟在 M7 正式发布前补验或重新形成正式范围决策。

> 2026-07-18 M7-06 首发范围决定：`1.0` 首发只保留客户自有公网云 Ubuntu Server 24.04 LTS x86_64。本地 Ubuntu 常开主机保持 `Candidate`；Windows 宿主 Ubuntu VM、Synology/NAS、macOS、ARM64、实体外接盘/NAS/设备 B、HID 扫码枪和针式打印机均为 `Deferred` 或 `Unsupported`，全部移出首发兼容清单。本决定不是将 M5-04、M5-05 或 M5-07 判定通过，本地平台仍无 `Certified` 结论；旧 Issue 按“1.0 不计划”关闭，未来恢复本地交付时必须新建版本化验收任务。

## 1. 目标与非目标

### 1.1 后续本地产品方向

- 用同一套完整 Copper 业务能力服务本地电脑、局域网常开主机和合格 NAS，不制造功能版本、用户数或软件容量差异。
- 让小微企业使用浏览器访问一台由自己控制的常开设备；数据库、附件、备份、恢复密钥和管理员权限仍归客户所有。
- 为每个正式支持目标提供精确的操作系统、CPU 架构、运行时、资源、网络、存储和已知限制，不依赖销售人员口头解释。
- 在写入业务数据前阻断不支持的环境；失败必须说明原因和可选解决路径。
- 设备故障后可以把整站备份恢复或迁移到另一台正式支持设备，不改变历史单据、库存、应收应付、资金、核销、附件和审计口径。
- 通过标准化预检、安装、HTTPS、备份和交接，验证未来本地/NAS 基础部署服务能否维持在 `¥649 起/生产环境` 的目标价格区间；该服务不属于 `1.0` 首发报价。

### 1.2 非目标

- 不承诺所有 Windows、macOS、Linux 发行版、NAS 品牌、型号和 CPU 架构。
- 不把员工日常办公电脑伪装成 7×24 服务器；设备睡眠、关机或带走时，局域网用户将无法访问。
- 不把 MySQL 在线数据目录放到 SMB、CIFS、NFS、WebDAV 或普通同步盘。
- 不在 M5 建设原生 Windows/macOS 桌面客户端，不直接管理打印机、扫描枪的专有驱动。
- 不以 UPnP、路由器端口转发、公网裸 IP 或暴露 MySQL/Backend 作为本地部署方案。
- 不因本地设备种类增加而降低 M1 至 M4 已冻结的数据库迁移、备份恢复、安全、审计和离线自主门槛。

## 2. 支持状态与宣传规则

| 状态 | 含义 | 对外口径 | 晋级/退出条件 |
| --- | --- | --- | --- |
| `Certified` 正式支持 | 指定硬件/OS/架构/运行时组合已完成全生命周期验收 | 可以列入正式兼容清单并按标准服务报价 | M5-07 证据齐全，限制已公开，成本可持续 |
| `Candidate` 候选支持 | 技术路线已冻结，仍在实现或缺少真实设备证据 | 只能称“计划支持/试点验证”，不得承诺标准交付 | 完成对应实现和真实设备验收后晋级 |
| `Deferred` 暂缓 | 方向可能合理，但当前设备、工件、维护或成本条件不足 | 不接标准部署；可在单独评估后决定是否试验 | 重新评估并建立独立验收计划 |
| `Unsupported` 不支持 | 已知会破坏安全、数据一致性或可维护性 | 安装前明确阻断 | 只有重新完成架构评审才能改变 |

强制规则：

1. 销售页、价格表、合同、安装器和运维文档必须引用同一份兼容清单。
2. “Docker 能启动”不等于正式支持；模拟器、QEMU 或开发机冒烟不能替代真实设备。
3. 支持对象是完整组合，不是单一品牌名。例如“Synology”不能替代 DSM 版本、具体型号、CPU、内存、文件系统和 Container Manager 版本。
4. 客户设备超出精确组合时，先执行只读评估；未通过不得以标准部署名义收费后再人工救火。
5. M7-06 完成时，本地目标没有任何 `Certified` 组合；既有正式形态证据只覆盖客户云/服务器路径，不能外推到办公室本地主机、Windows VM 或 NAS。

## 3. 决策摘要

| 编号 | 决策 | 强制结果 |
| --- | --- | --- |
| M5-ADR-01 | 正式支持以真实设备全生命周期证据为准 | 没有 M5-07 证据的平台保持 Candidate/Deferred |
| M5-ADR-02 | 保持“一个常开服务端 + 多浏览器客户端”拓扑 | 不为 Windows/macOS/NAS 复制业务代码或建设功能不同的桌面版 |
| M5-ADR-03 | 第一优先候选是 Ubuntu 24.04 x86_64 本地常开主机 | 最大化复用 M1 至 M4 已验证的 Compose、升级、备份和安全能力 |
| M5-ADR-04 | ARM64 必须使用正式多架构工件 | amd64 镜像在模拟层“能跑”不能宣传 Apple Silicon/ARM NAS 支持 |
| M5-ADR-05 | 局域网正式业务访问强制 HTTPS | HTTP 仅允许 80 到 443 跳转、证书挑战或不处理秘密的本机安装引导 |
| M5-ADR-06 | 稳定 IP/DHCP 保留或受控 DNS 是正式地址 | mDNS/`.local` 只能作便利入口，不能成为证书和备份身份的唯一依据 |
| M5-ADR-07 | 主数据使用本地可靠块存储，备份使用独立介质 | SMB/NFS 可作备份目标，不得作 MySQL 在线数据目录 |
| M5-ADR-08 | 打印与扫码采用浏览器/操作系统成熟路径 | 首期打印走系统打印；扫码只正式验收键盘模拟 HID |
| M5-ADR-09 | 休眠即服务中断 | 多人长期使用推荐常开小主机或 NAS；办公笔记本只适合明确接受停机的场景 |
| M5-ADR-10 | `¥649 起` 只覆盖标准兼容清单和固定交付边界 | 硬件、系统重装、复杂网络/证书、专有驱动和历史数据清洗单独报价 |
| M5-ADR-11 | Windows 只作为 Ubuntu x86_64 虚拟机宿主 | 不建设 Windows 原生、WSL2 或 Docker Desktop 安装器；虚拟机内复用同一 Ubuntu 交付合同 |
| M5-ADR-12 | `1.0` 首发采用客户云单一环境范围 | 本地/LAN、Windows VM、NAS、ARM64、macOS 和延期外设全部移出首发；保留工程资产但不宣传、不报价、不接标准交付 |

## 4. 候选支持矩阵与优先级

### 4.1 现阶段矩阵

以下资源是 M5 实施和采购测试机的起始门槛，不是已发布的正式兼容清单。硬门槛和推荐值必须由 M5-07 的真实数据最终确认。

| 优先级 | 目标组合 | 当前状态 | 起始硬门槛 | 推荐配置 | 运行时与主要限制 |
| --- | --- | --- | --- | --- | --- |
| P0-A | Ubuntu Server 24.04 LTS x86_64 本地常开主机/迷你服务器 | Candidate（移出 1.0） | 2 核、4 GiB、20 GiB 可用本地盘 | 4 核、8 GiB、100 GiB；有线网络和 UPS | Docker Engine 29.x、Compose 5.x；未来必须完成实体 LAN、休眠/重启、迁移和恢复后才能晋级 |
| P0-B | 指定型号 Synology DSM 7.2.1+ x86_64 + Container Manager | Deferred（移出 1.0） | 4 GiB、20 GiB 可用内部存储池 | 8 GiB、100 GiB；Btrfs/ext4 内部卷、UPS | 当前无真实型号证据；只接受逐型号验收 |
| P1 | Windows 11 x86_64 宿主 + Ubuntu Server 24.04 x86_64 虚拟机 | Deferred（移出 1.0） | 宿主 8 GiB；客体 2 核、4 GiB、20 GiB 本地虚拟磁盘 | 宿主 16 GiB；客体 4 核、8 GiB、100 GiB；有线网络、禁用服务时段睡眠 | 当前未完成精确虚拟化产品的桥接、自动启动、宿主重启和防火墙实体证据 |
| P2 | macOS + Apple Silicon | Unsupported（服务端安装） | 不适用 | Mac 可继续作为受支持浏览器客户端 | `1.0` 不使用 Docker Desktop 交付 Copper 服务端；多架构镜像可构建不等于 macOS 服务端受支持 |
| P3 | Synology ARM64、QNAP、其他 NAS、Intel Mac、其他 Linux 发行版 | Deferred（移出 1.0） | 未冻结 | 未冻结 | 需真实客户需求、精确型号和独立维护成本评估 |
| - | 32 位系统、低于硬门槛、MySQL 数据目录位于网络共享、无法控制管理员/证书/备份密钥的设备 | Unsupported | 不适用 | 不适用 | 安装前 fail-closed |

### 4.2 平台选择理由

- 以下顺序仅作为未来重启本地产品线时的技术评估顺序，不属于 `1.0` 首发承诺。
- Ubuntu x86_64 是第一目标，因为现有正式发布物、MySQL 8.4、Compose、升级、备份、安全和故障演练都来自同一 Linux 运行合同；M5 只需增加本地网络、外接盘和外设验收，风险最低。
- Synology x86_64 排在 Windows 前，是因为 NAS 更符合“常开、局域网共享、独立存储”的使用习惯；但只能逐型号认证，不能从 Container Manager 存在推导所有群晖可用。
- Windows 客户统一运行 Ubuntu x86_64 虚拟机，避免维护第二套 Windows/WSL2 安装和数据合同；但宿主更新、虚拟化产品、虚拟机自动启动、桥接/转发、防火墙和睡眠仍须实测。
- Apple Silicon 的 linux/arm64 镜像仍可作为发行工程资产，但 `1.0` 不建设或支持 macOS Docker Desktop 服务端安装；Mac 只作为浏览器客户端使用。
- Intel Mac、其他 NAS 和低配设备优先级低，避免为缩小中的平台或不可控厂商差异长期承担低价人工维护。

## 5. 统一本地部署拓扑

```text
同一受控局域网中的浏览器
    |
    | HTTPS :443
    v
稳定 IP / 受控 DNS 名称
    |
Caddy / 正式 TLS 入口
    |-- Copper Web
    `-- 同源 /api --> Backend --> MySQL 8.4
                         |            |
                         |            `-- 本地可靠数据卷
                         `-- 本地附件卷

客户管理员 --> copperctl --> 预检、启动、状态、升级、备份、恢复
                                      |
                                      |-- 独立外接硬盘
                                      `-- 已由操作系统挂载的 NAS 备份目录
```

### 5.1 不变的业务和安全合同

- Web、Backend、MySQL、Flyway、备份、恢复和导出仍由同一版本清单与不可变摘要绑定。
- 浏览器只访问同源 HTTPS；MySQL 和 Backend 内部端口不映射到 LAN。
- 后端继续承担权限、数据范围、业务状态、十进制金额、并发和审计的最终校验。
- 本地平台差异只进入安装、运行时、网络、存储和外设适配层，不进入采购、库存、销售、资金和核销业务模型。
- 本地部署不引入远程许可证心跳、强制遥测或 Copper 官方云控制面。

## 6. 安装前设备采集与预检合同

### 6.1 客户设备采集表

进入报价或试点前至少记录：

1. 设备品牌、完整型号、CPU 型号/架构、内存、系统盘和数据盘容量。
2. Windows/macOS/Ubuntu/DSM 的完整版本与补丁；Docker/Container Manager/虚拟化产品及版本。
3. 数据卷文件系统、磁盘加密、RAID/存储池、S.M.A.R.T. 和 UPS 情况。
4. 是否常开，默认睡眠/休眠/自动更新/断电恢复策略，谁能执行管理员操作。
5. 路由器、DHCP 保留、本地 DNS、VLAN、客户端数量、浏览器和远程访问诉求。
6. 打印机品牌/型号/连接方式、扫码枪品牌/型号/是否键盘模拟、文件上传规模。
7. 备份目标类型、位置、容量、挂载方式、恢复私钥保管人和异地副本。
8. 是否存在历史系统迁移、专有驱动、域控、代理、防火墙或监管限制。

### 6.2 机器预检顺序

预检必须只读且先于数据目录创建：

1. 匹配精确支持矩阵组合，验证 OS build、架构和运行时。
2. 验证 CPU/虚拟化、可用内存、磁盘空间、文件系统和写入/原子重命名能力。
3. 拒绝网络共享上的 MySQL/附件主数据目录，识别同步盘和可移除盘误选。
4. 检查 80/443 和内部端口冲突；确认 MySQL/Backend 不会对 LAN 暴露。
5. 检查稳定地址、客户端到 443 的路径、时间同步和证书方案。
6. 检查开机/登录后启动、睡眠和断电恢复能力。
7. 检查独立备份目标、剩余容量、挂载身份、权限和恢复密钥准备状态。
8. 输出 `PASS`、`FAIL` 或 `MANUAL_REVIEW`，附机器可读证据和用户可理解的修复建议。

任一安全或数据一致性硬门槛失败时，不得继续“试试看”；手工绕过必须转为非标准环境评估并留下风险确认。

## 7. 局域网、HTTPS 与名称解析

### 7.1 地址和访问

- 正式入口使用 DHCP 保留的稳定 IP，或客户控制的本地/公共 DNS 名称指向该私网 IP。
- `.local`/mDNS 可以帮助首次发现，但名称冲突、跨 VLAN 和证书信任不可控，不能作为唯一正式地址。
- 路由器、VLAN 和客户端防火墙由客户控制；标准交付只覆盖同一受控 LAN，不自动包含跨网段、VPN 和公网远程访问。
- Windows 宿主场景只有在 Ubuntu 虚拟机使用稳定私网地址，并且桥接网络或受控 80/443 转发、宿主防火墙和客户端访问通过实测后，才可对 LAN 宣布可用。

### 7.2 TLS

- 多用户 LAN 正式业务必须使用 HTTPS，保持 `Secure`、`HttpOnly`、`SameSite` Cookie 和 M4 安全响应头合同。
- 优先顺序：客户受控内部 CA/MDM 分发证书；客户域名配合 DNS-01 获取受信证书；最后才是逐客户端导入的本地 CA。
- 本地 CA 的根证书、站点证书私钥、轮换、吊销、丢失恢复和客户端信任范围必须交接，不得把“浏览器点继续”当作安全方案。
- HTTP 只允许 80 到 443 跳转、ACME 挑战，或同机回环上的无秘密安装引导；不得在 HTTP 上登录、上传业务文件或传输经营数据。
- 禁止默认配置路由器端口转发、UPnP 或公网裸露。需要外网访问时另行使用受支持 VPN/零信任接入并专项评估。

## 8. 存储、备份与迁移

### 8.1 主数据

- MySQL、附件、运行配置和审计证据使用本机/本 NAS 的可靠块存储；容器重建不得删除。
- Windows 宿主场景的数据留在 Ubuntu 虚拟机的可靠本地虚拟磁盘，不把 MySQL 数据放到 Windows 共享文件夹、OneDrive、SMB 映射盘或虚拟机共享目录。
- Synology 作为应用主机时只能使用已验收的内部存储池；另一台 NAS 或同 NAS 的不同备份存储位置仍只是备份目标。
- 外接 USB 盘默认只作备份，不作在线数据库盘；意外拔出不得让业务返回假成功。

### 8.2 备份目标

- 至少推荐一个与主数据故障域分离的目标：独立外接盘、另一存储池、另一台 NAS 或客户 S3 兼容对象存储。
- NFS/CIFS 由操作系统管理员预先挂载；Copper 不保存 NAS 管理员密码，也不负责绕过 NAS 权限。
- 挂载点必须校验设备/共享身份、文件系统、可写性和容量。缺盘、换盘、只读、满盘或权限变化时 fail-closed，不得把文件写入空的本地挂载目录后宣称 NAS 备份成功。
- 备份继续使用 M2 的一致性、加密、清单、摘要、原子发布和客户离线持钥合同。
- 唯一恢复私钥不得只保存在应用主机或唯一备份盘；交接时至少验证一次真实解密恢复。

### 8.3 换机迁移

设备 A 到设备 B 的标准迁移顺序固定为：

1. 目标设备通过精确兼容预检；
2. 来源设备生成并验证最新一致性整站备份；
3. 目标设备旁路恢复，不覆盖正在运行的来源站；
4. 复核版本/Flyway、表数量、附件、审计、库存、应收应付、资金和核销不变量；
5. 人工切换稳定地址并验证 LAN、打印、扫码和上传；
6. 保留来源站和回退窗口，客户确认后才执行危险清理。

CPU 架构变化不能改变业务数据格式；跨 amd64/arm64 迁移依赖两边发布物和目标平台均已正式支持。

## 9. 多用户、打印、扫码、上传与离线边界

### 9.1 多用户

- 至少两台独立客户端并发验收登录、查询和写操作；后端权限、数据范围、重复提交、版本冲突和审计结果必须正确。
- 设备资源门槛按并发用户、附件规模和数据量复测，不能从单浏览器冒烟推导多人容量。
- 主机休眠、关机、重启或网络中断时，客户端必须明确显示“主机不可达/正在恢复”，不能缓存假成功。

### 9.2 打印

- 首期使用浏览器 `window.print()` 和操作系统已安装的打印机；Copper 管理单据打印样式、分页和内容口径，不管理厂商驱动、墨盒、网络打印机维修。
- 至少验收一台常见 A4 打印机的采购、销售、出入库等关键单据；状态、数量、金额和来源口径必须与详情一致。
- 热敏标签、套打、云打印、静默打印和专有控件属于后续独立需求，不得混入 `¥649 起` 标准交付。

### 9.3 扫码枪

- 首期只承诺通过键盘模拟输入的 USB/Bluetooth HID 扫码枪；扫码结果仍由业务页面校验商品、批次、数量、状态和重复码。
- 必须覆盖中文输入法、焦点丢失、连续扫码、回车后缀、重复扫码、未知码和页面切换。
- 串口、WebUSB、厂商 SDK、称重设备和工业 PDA 在精确型号验收前为 Deferred。

### 9.4 上传与断网

- 文件上传走同源 HTTPS，覆盖大小/类型限制、网络中断、重试、防重复和失败后保留表单；数据库元数据与文件原件必须一起成功或明确失败。
- 互联网中断但 LAN 和主机仍在线时，Copper 核心业务继续运行；主动选用的 OCR、短信、S3、Webhook 等外部能力明确降级。
- LAN 中断或主机休眠不等于“离线可用”；客户端不会在本地复制一套可独立记账的数据，避免离线冲突破坏库存和资金口径。

## 10. 平台专项边界

### 10.1 Ubuntu 本地常开主机

- 复用现有 Ubuntu 24.04 x86_64、Docker Engine、Compose、systemd、Caddy 和 `copperctl` 合同。
- M5 新增本地磁盘身份、局域网 HTTPS、外接盘/NAS 备份、UPS/断电、打印和扫码验收。
- 如果需要长期多人访问，推荐专用小主机而不是员工办公电脑；硬件故障、UPS 和磁盘更换仍由客户负责。

### 10.2 Synology

- Container Manager 支持以 Compose 项目管理容器，但正式支持必须绑定具体 NAS 型号、DSM/Container Manager 版本、CPU、内存和内部存储池。
- 不直接修改 DSM 系统组件，不把 DSM 管理端口当作 Copper 业务入口，不要求客户开放 NAS 管理界面到公网。
- DSM/Container Manager 更新前执行备份和兼容预检；休眠、端口占用、权限、反向代理和 UPS 行为必须逐型号验证。

### 10.3 Windows 宿主 + Ubuntu 虚拟机

- Copper、Docker、MySQL、配置、附件和备份状态全部位于 Ubuntu Server 24.04 x86_64 虚拟机内；不在 Windows 原生、WSL2 或 Docker Desktop 中安装 Copper。
- 虚拟机客体复用 Ubuntu 的 `copperctl`、systemd、Compose、备份和恢复合同；Windows 宿主不保存 Copper 数据库密钥或客户恢复私钥。
- 正式验收必须绑定精确 Windows 版本、虚拟化产品/版本、虚拟机配置和虚拟磁盘位置。虚拟机应随宿主机启动，不依赖用户登录后手工开启。
- 局域网入口使用桥接网络或受控的 80/443 转发；仅宿主或客体 localhost 可访问不算通过，3306/8191 仍不得暴露。
- Windows 更新、睡眠、重启、异常断电、虚拟机自启动、网络恢复和磁盘容量必须形成可复现验收；无法保证常开时不得作为多人正式服务器。

### 10.4 macOS Apple Silicon

- 只评估 Apple Silicon，不为 Intel Mac 建立新的长期正式基线。
- 候选运行时为 Docker Desktop，使用正式 linux/arm64 工件；不得默认用 amd64 模拟运行正式生产。
- 只覆盖 Docker 官方当前支持的 macOS 范围，并记录具体主机、macOS 和 Docker Desktop 版本；系统升级后需重新验证。
- Mac 休眠、合盖、FileVault、磁盘空间、自动更新、LAN 入站和 Docker Desktop 许可是正式支持门槛。
- 所有验证使用专用测试设备，不在开发者 Mac 安装或运行 Docker、Colima、Docker Desktop。

## 11. `¥649 起` 标准服务边界

### 11.1 标准范围

只有设备位于当期 `Certified` 兼容清单且预检通过时，`¥649 起/生产环境` 才包含：

- 一台主机、一个 Copper 站点、一个受控局域网的远程标准安装；
- 标准运行时、开机/登录后启动、稳定地址和 HTTPS 入口配置；
- 首次管理员一次性凭据交付与销毁；
- 一个客户已准备好的外接盘或 NAS 备份目标配置；
- 一次完整备份和空白旁路恢复验证；
- 最多三台客户端的浏览器/证书信任接入验证；
- 一台已被操作系统正常识别的打印机基础打印验证；
- 一把标准键盘模拟扫码枪基础输入验证；
- 标准交接记录和客户责任说明。

### 11.2 不包含

- 电脑/NAS、硬盘、UPS、路由器、交换机、域名、证书商业费用和 Docker Desktop 商业许可；
- 操作系统重装/升级、RAID 修复、磁盘救援、综合布线、跨 VLAN、VPN、公网远程访问和域控策略；
- 打印机/扫码枪专有驱动维修、标签模板、套打、静默打印、串口/WebUSB/厂商 SDK；
- 历史数据清洗迁移、第三方接口、定制开发、长期监控和无限售后；
- 超出正式兼容清单的环境。

不兼容时必须在收费实施前停止。客户选择非标准环境时，使用 `¥150/小时或固定报价`，先书面确认风险、退出条件和可交付结果；不能在标准价内无限排障，也不能通过删除备份、HTTPS或恢复验收来维持低价。

## 12. Candidate 晋级 Certified 的证据门槛

每一个精确平台组合必须独立完成：

1. 记录真实设备、OS/DSM、CPU、内存、磁盘、文件系统、运行时和网络版本。
2. 从合入三仓 `main` 的不可变工件全新安装，验证首次凭据交付和销毁。
3. 验证停止/启动、容器重建、主机重启、睡眠/唤醒、异常断电等价终止和自动恢复。
4. 从最近受支持来源版本完成升级；故障时保持来源站可用并验证回滚。
5. 完成一致性备份、不可读/断盘/满盘失败、空白恢复和跨设备迁移。
6. 使用至少两台客户端验收 HTTPS、权限、并发、打印、扫码和上传。
7. 阻断公共互联网，验证核心采购、库存、销售、收付款、查询及第三方降级。
8. 扫描端口、秘密、Cookie、日志、审计、容量和健康状态。
9. 记录安装/恢复/升级的人工与机器耗时、失败次数、第三方许可和后续支持次数。
10. 形成脱敏证据包、已知限制和支持生命周期，经 PR 评审合入 `main`。

任一数据安全、网络安全、升级恢复或成本门槛失败时，平台不得晋级；可接受限制必须写进兼容清单和客户验收单，不能留作内部口头知识。
