# 往来单位停用与最终过账保护

2026-10-16。

往来主体启停、`type_mask` 身份集合及对应客户/供应商资料状态，在每次新增经营事实前统一校验。事务内先以共享锁读取往来主档，再以共享锁检查对应身份资料；`updatePartner` 使用同一主档的排他锁，然后维护身份状态，避免“确认时读取启用，停用随后提交，旧草稿继续过账”的竞态。直运同时涉及两个主体，先按主键顺序锁定。共享锁允许正常业务并发和不同单据锁顺序，避免新增业务对往来主档抢排他锁造成编辑/确认或收款/发货死锁。信用敞口单独在 `sales_risk_policy` 主键上取排他锁，业务风控不把主档/身份共享锁升级；修改授信策略先取得主档排他锁。

保护覆盖购销建单和变更、入库审核、出库确认/定价、新退货、应收调整、预收占用、收付款、承兑新增资金处置、余额调整、费用/其他往来源单确认与实际收付款、直运发出及客户实收。权限范围检查继续独立执行。只读商品计量选项校验相同身份口径，不增加无必要的写事务。

已完成单据的幂等确认仍可返回原结果；拒绝、草稿作废、释放预收占用及反向冲正继续可用，历史读取不因主体停用而隐藏。主体停用原因在后端与前端均必填。原客户、供应商身份历史保护保持不变。

`COPPER_PARTNER_SAFETY_E2E=true` 启用两组真实 MySQL 验收：`PartnerPostingSafetyMySqlAcceptanceTest` 在回滚事务内验证入库、出库、余额、主档原因、身份单一口径、费用收付款、直运两端状态及安全反向操作；`PartnerBusinessGuardConcurrencyMySqlAcceptanceTest` 使用独立事务证明过账等待停用提交并读取最新状态、正常采购编辑/确认不会因单据与主档锁顺序相反发生死锁、并发信用检查不会把主档/身份共享锁升级，最后清理唯一夹具。

15 类商品验收进一步逐类验证退货后的客户收款、供应商付款、两侧来源核销及应收应付归零；不能仅以品类出现在页面或商品保存成功作为完整经营链路验收。

包装标签 OCR 的实重保持标签原始数值精度，不能按金额两位小数截断。`actual_weight_kg` 仍明确是 kg，前端进入商品主库存单位前需按受控单位换算，并经过人工确认。
