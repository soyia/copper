# 0.4.0-rc.7 后端与当前实库验收

日期：2026-10-16。状态：本次开发交付验收通过，源码组合由 Deploy 的 rc.7 冻结记录绑定。本记录不将源码候选冒充已安装的运行镜像。

## 业务修复与数据库收口

- 统一校验往来单位主档、`type_mask` 与客户/供应商身份状态。业务确认取共享当前读，停用取主档排他锁；编辑与确认、收付款与风控不因新增主档锁产生相反锁序或锁升级。停用后拒绝新的库存、资金和直运过账，已完成单据重放、拒绝、作废、冲正和历史查询仍可用。
- Web 数量、实重和单位换算按后端六位数量口径收口；后端 OCR 保留标签原有精度。单价和金额继续使用各自的精度规则，不能将数量精度套到金额。
- V67 在完整孤儿预检后增加 54 条限制删除/更新的外键，全库实际为 92 条。既有 V57/V58 的 InnoDB `NO ACTION` 保留原始元数据；恢复验证仅在实际 MySQL 8.4 和父子表均为 InnoDB 的证据下接受其立即限制语义。
- V68 修复旧单据 ID 与新明细 ID 的包装引用碰撞。保留既有引用、用全部历史引用及当前自增高水位划定新号段，增加唯一索引；重复引用、零引用或 Long 范围耗尽在表 DDL 前明确阻断。冲正读取同时限定批次与商品。
- V1–V66 未修改。本轮没有删除历史单据、重写业务事实、补造会计过账批次或自动修复归属不明的数据。

详见 [往来单位过账安全](PARTNER_POSTING_SAFETY.md)、[核心引用完整性](CORE_REFERENTIAL_INTEGRITY_BASELINE.md) 和 [包装引用身份](NON_TRADE_PACKAGING_REFERENCE_IDENTITY.md)。

## 实际验证

| 验证 | 结果 |
|---|---|
| 单元与契约 | 227 项通过，零失败/跳过 |
| 当前经营真实 MySQL | 22 个测试类、97 项通过，零失败/跳过 |
| V67 新装、已有库升级与脏数据拒绝 | 5 项通过 |
| 独立持久业务恢复夹具 | 1 项通过；正式领域服务真实提交 |
| 恢复外键交叉核验 | 78 个核心映射通过，92 条实际外键全部零孤儿 |

97 项实库场景包含十五类商品各自建档、购销、收发货、双向退货、收付款和来源核销，六位数量、实重包装及部分领用，授信/ATP 并发、期初迁移、税票银行关账、直运、停用与正常经营竞争，以及 V68 的升级、碰撞拒绝和跨单冲正保护。

运行环境为独立原生 MySQL 8.4.11 和 Java 17，数据库、文件和凭据均使用本轮拥有的临时资源。数据库端口为回环地址 33067；没有启动或停止正式 8191，也没有修改现有业务库。

复跑经营链使用 `tests/run-current-release-mysql.sh`，只接受 `copper_release_acceptance_*` 专用库，按当前报告时间校验每个预期测试类，任何失败或跳过均不通过。核心迁移入口为 `tests/run-core-referential-integrity-mysql.sh`。持久恢复夹具必须另行显式开启 `COPPER_RELEASE_RECOVERY_FIXTURE=true`，只允许 `copper_release_acceptance_recovery_*` 空业务库，禁止加入普通可回滚经营测试。

## 已提交业务的加密逻辑恢复

恢复夹具通过正式服务完成采购、入库、销售、出库、部分收付款和合成图片上传，实际形成 7 个业务过账、5 张自动生成凭证；库存 `8.123455`、未收 `60.25`、未付 `307.42`。一个上传原件及其审核快照形成两个文件和两个附件引用。

随后实际执行 MySQL 全库逻辑导出，将数据库和附件一并归档，使用临时演练公钥加密、私钥解密，在新建独立库和目录恢复。256 张表、3,999 条记录的完整行内容、生产行数/业务汇总/十类附件引用、逐文件 SHA-256、92 条外键及 V68 唯一索引和自增计数器全部一致；源库未变，恢复目标和临时私钥已清理。

这是原生 MySQL 加密逻辑恢复补验，不冒充 Linux Compose 整站安装、`copper-backup/v1` 正式包、当前不可变镜像或客户正式持钥验收。证据见 [恢复 JSON](RELEASE_LOGICAL_RECOVERY_20261016.json) 和 [汇总 JSON](RELEASE_ACCEPTANCE_20261016.json)。
