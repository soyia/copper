# Copper 0.3.0-rc.2 发布说明

> 渠道：内部验收 / 明确同意的试点 RC

## 候选顺延说明

- `0.3.0-rc.1` 的镜像标签已经生成但没有对外发布；最终验收发现 Web 工作流缺少可供无 GHCR Token 验收机使用的源码绑定离线镜像 artifact，因此该候选停止，不移动、不覆盖既有标签和摘要。
- `0.3.0-rc.2` 从新的 Web `main` 提交重新构建前后端镜像，并要求两个组件都交付确定性 gzip 归档、`SHA256SUMS` 和绑定 source commit、workflow run、镜像摘要、平台的 `image-evidence.json`。

## 安全与供应链变化

- Web 构建运行时升级到 Node.js 22.22.3，运行时升级到 Caddy 2.11.4；固定基础镜像摘要，并从最终镜像删除不使用且带来 Critical 扫描结果的 `curl`。
- Backend 升级到 Spring Boot 3.5.16 / Tomcat 10.1.55；普通消息和异常栈统一经过最终 Logback 脱敏出口。
- Caddy 访问日志删除认证、Cookie、来源和 User-Agent 字段，遮蔽敏感查询参数并掩码客户端 IP；`copperctl logs` 提供额外的结构化/文本脱敏层。
- 新增数据库业务/root 口令计划轮换、失败恢复、秘密生命周期登记和宿主机秘密审计。
- MySQL 继续使用 Compose secret 的 `*_FILE`，并在官方初始化完成、最终启动 `mysqld` 前清除读取出的明文口令环境变量；上游入口结构变化时失败关闭。
- 发布工厂固定 Syft、Grype、Gitleaks 镜像摘要，为三仓源码和三张 amd64 镜像生成六份 CycloneDX SBOM、漏洞报告、秘密扫描与不可变安全证据包。
- RC 和稳定版均阻断未处置 Critical；稳定版额外阻断 High。漏洞数据库必须有效且不超过 72 小时，任何真实秘密发现均失败关闭。

## 数据库与经营数据影响

- 数据库从 schema 4 升级到 schema 5，仅追加已经随 M4-02 Backend 发布的 `V5__security_session_audit.sql`；不修改 V1-V4 历史迁移。
- V5 为登录会话追加撤销时间、原因和操作人，为用户追加密码变更时间，并为安全审计追加独立事件 ID、结果/失败码、会话、追踪、请求和主体哈希字段及索引。
- V5 不修改库存、批次、应收应付、收付款、发票、附件和历史经营单据口径；既有安全审计行只补齐可追踪字段，不伪造经营或资金流水。
- 从 `0.2.0-rc.1 / schema 4` 升级必须在加密整站备份后使用保留旁路站执行 V5 和验证，属于维护窗口；禁止按 image-only 短暂重启处理。
- 数据库口令轮换是独立维护操作，不在普通版本升级中自动执行；轮换前停止 Web/Backend，失败时恢复数据库账户、秘密文件和服务。

## 支持的直接升级

- 仅支持 `0.2.0-rc.1 / schema 4` 直接升级到 `0.3.0-rc.2 / schema 5`。
- `0.3.0-rc.1` 未通过完整交付门槛，不作为已部署来源列入升级矩阵。
- 其他来源版本或 schema 未在本候选中声明支持，预检必须拒绝；更早版本应先按其已验收矩阵升级。
- schema 已变化，回退只能切回完整保留的旧站旁路，或使用升级前已验证的 `copper-backup/v1`；禁止逆向 SQL 或只换回旧 Backend 镜像。

## 已知限制与 RC 风险

- MySQL 8.4.10 官方镜像当前在一次性降权工具 `gosu` 中被 Grype 报告三项 Go 标准库 Critical；二进制 `govulncheck` 原始输出包含 41 个包/模块级发现对象，但没有函数符号可达路径。仅允许在最长 7 天、具名责任人与补偿控制的 RC 例外中验证；这不是“无风险”结论，稳定版继续阻断。
- High/Medium/Low 发现、责任人和修复期限进入安全证据，不得通过删除报告或移动标签规避。
- 本版本不改变客户数据所有权、导出、备份、离线部署或自主升级边界，不引入遥测、许可证心跳或 Copper 托管密钥服务。
