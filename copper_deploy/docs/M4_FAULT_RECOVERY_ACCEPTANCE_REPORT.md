# M4-06 故障恢复与经营财务不变量验收报告

> 验收日期：2026-07-15
> 跟踪任务：<https://github.com/soyia/copper_deploy/issues/35>

## 1. 验收范围与边界

本项在隔离的 Ubuntu Server 24.04 LTS x86_64 主机上，使用 MySQL 8.4、正式 Compose 拓扑和真实容器，依次注入数据库不可用、磁盘预警/严重/耗尽、备份目标失败、证书过期、系统时间跳变以及异常断电等价终止。开发者 Mac 未运行 Docker、Colima 或 Docker Desktop，宿主机端口 8191 始终未被占用。

本报告证明这些已覆盖故障能够明确失败、恢复并保持本次样本的不变量，不承诺零数据丢失、零停机、任意硬件故障自动恢复或商业 SLA。异常断电使用 MySQL、Backend、Web 容器 `SIGKILL` 作为主机掉电等价故障；物理云盘损坏、跨可用区灾难和完全断网退出验收仍不在本项范围。

公开报告不记录主机 IP、SSH 私钥、密码、Token 或客户数据。完整证据仅保留在验收主机的 root-only 目录。

## 2. 新增安全控制

- Deploy 在应用不可写的独立目录中以 root 生成原子写入的 `copper-time-safety/v1` 快照，并只读挂载给 Backend；快照记录 boot ID、单调时钟、墙上时钟、NTP 同步和偏差等级，大于等于 60 秒的跳变进入锁存 `BLOCKED`，直到 NTP 真正恢复。
- Backend 仅信任安全权限下的新鲜快照。时间不可信时，财务、权限、导出及订单/入出库状态流转等高风险写入明确失败；普通低风险操作不被无差别停机。
- 容量检查和本地监控均在判断前刷新时间快照，监控显示当前等级及触发阻断的原始最大跳变。
- 故障演练日志采用 `copper-fault-drill-event/v1`，逐事件记录故障、阶段、结果、数据影响、人工步骤和遗留风险，并以 SHA-256 前向哈希链及单调时钟固定顺序。
- 自动化脚本使用独立数据盘、备份盘和 ENOSPC 小盘，完成故障注入、恢复、不变量复核、证据清单和现场清理。

## 3. 六类故障结果

| 故障 | 发现至恢复 | 安全失败与数据影响 | 恢复动作 | 遗留风险 |
| --- | ---: | --- | --- | --- |
| 数据库不可用 | 38.498 秒 | API 明确失败，失败尝试未写业务行；恢复后显式重试只写一行 | 重启 MySQL 并等待 Compose 三层健康 | 失败响应速度仍受连接池超时影响 |
| 磁盘预警/严重/耗尽 | 2.089 秒 | 分级状态真实出现；阻断期写入被拒绝，无数据库或附件损坏；独立 ext4 小盘真实触发 ENOSPC | 删除本次受控填充文件或扩容，再复查监控 | 正式清理不得删除业务、审计、附件或唯一成功备份 |
| 备份失败 | 26.621 秒 | 只读目标导致失败；未更新最后成功时间、未发布半包、未删除旧成功包 | 修复目标、复核旧包、显式重试并验证新包 | 同期旧包仅能在新包提交并验证后按策略清理；本机备份不能覆盖整机损失 |
| 证书过期 | 1.404 秒 | 过期证书被识别，未降级到公网 HTTP，80/443 未形成旁路 | 更新证书并复查链、主机名和监控 | 外部代理仍依赖客户 DNS、证书和代理可用性 |
| 系统时间异常 | 23.737 秒 | 主机真实前跳 120 秒后锁存阻断；高风险财务写入失败且未产生账务变化 | 恢复 NTP、刷新快照、复核审计，再显式重试 | 故障窗口的墙上时间不可信，哈希链单调顺序才是权威顺序 |
| 异常断电等价终止 | 23.067 秒 | 未提交事务未出现，已提交行和附件未丢失 | 等待 MySQL crash recovery，完整比对后再放开写入 | `SIGKILL` 是本项接受的掉电等价故障；M4-07 仍需最终空白机退出验收 |

故障事件共 36 条，六类结果均为 `PASSED`。系统时间跳变会使该故障窗口内的 `occurredAt` 非单调，这是预期证据；恢复耗时和先后关系使用同一 boot 内的 `monotonicSeconds` 计算，不能用墙上时间倒序误判证据造假。

## 4. 恢复后不变量

- Flyway schema 为 5，恢复前后迁移历史完全一致。
- 90 张表逐表执行 `CHECK TABLE`，90 项全部为 `OK`；表结构、记录数和业务汇总的精确快照一致。
- 商品、单位、仓库、往来单位、采购、入库、销售、出库、退货、库存批次/流水/余额、应收应付、预收预付、资金流水和核销关系按本次固定样本逐项比对，无重复、丢失或无痕覆盖。
- 已提交业务、财务和审计记录保持一致；时间阻断期的财务请求未产生账务行，异常终止前未提交事务在恢复后不存在。
- 附件稳定路径、字节数和 SHA-256 一致，历史引用未断裂。
- 40 项应用级业务引用/孤儿检查恢复前后均为 0。

必须明确记录的结构风险：当前 schema 声明的数据库外键约束数量为 0。本次 40 项检查只能证明固定业务关系在该样本中没有孤儿，不能替代数据库外键强制约束，也不能证明未列出的未来关系天然安全。M4-06 不在故障演练中临时改表；该风险应作为后续数据模型治理输入，在正式 Flyway 迁移、历史脏数据预检、回滚和性能验证完整后再收紧约束。

## 5. 演练中发现并修复的问题

1. Backend 新增第二构造器后，生产构造器缺少显式注入声明，真实容器启动失败；已补充明确注入并增加回归测试。
2. 备份验收脚本最初混用相对/绝对成功包路径，并错误假设同日旧包必然保留；已按正式状态和“新包验证后才允许保留策略生效”修正。
3. 时间跳变第一次被发现后，后续采样会降级原始危险事实；现已锁存阻断并保留原始最大跳变，直到 NTP 真实恢复。
4. 单次 `makestep` 不足以稳定恢复大偏差；清理流程改为多轮采样、burst、makestep 和同步复核，最终自动恢复 NTP。
5. 备份元数据工具入口、MySQL 8.4 缺少 `mysqlcheck` 客户端及事务探针把自身连接计入等脚本偏差均在继续验收前修正；最终使用服务端逐表 `CHECK TABLE` 和排除当前连接的事务探针。

这些失败均发生在相应安全门槛之前，没有被写成通过证据，也没有跳过恢复步骤继续后续故障。
