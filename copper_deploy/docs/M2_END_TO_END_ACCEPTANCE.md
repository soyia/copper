## 4. 第一方向：本地来源到客户云

原整站备份在空白 AWS x86_64 站点完成以下链路：

1. 外层 SHA-256、envelope、加密载荷、离线证明、站点 ID、镜像摘要和 V3 结构全部通过。
2. 旁路 MySQL 导入后，全部表记录数、外键、经营财务汇总和附件合同与备份一致。
3. Backend 和 Web 只有在数据合同通过后才启动健康；35 秒进入 `VALIDATED`。
4. 未登录旁路实例，直接执行 `SWITCH copper-m207-source m207-final`；切换后正式三层健康。
5. 执行 `ROLLBACK copper-m207-source m207-final` 后，原空白站恢复健康；采购、入库、销售、出库、库存批次、付款和回款均为 0，证明回滚没有混入恢复数据。

## 7. 三存储目标组合验收

M2-07 不重复在中国区主机临时搭建对象存储。M2 的三目标退出证据由 M2-05 已合并的运行时验收与本轮 x86_64 跨环境验收组合形成：

- M2-05 在 `local-database` 使用独立本地目录、bind-mount NAS 和固定摘要 MinIO，验证同一 51,200 字节 `copper-backup/v1` 在三个目标中的字节和 SHA-256 完全相同。
- 已验证 NAS 断线、退化为本地目录、只读、空间不足，以及 S3 凭据错误和超时均安全失败，不覆盖最近成功状态。
- 本轮 AWS 又验证本地正式目标上的 4,208,640 字节真实业务备份可离线读取、跨环境恢复、切换、回滚和再次迁移。

据此满足“两个迁移方向、三个存储目标”的 M2 组合门槛；不把 MinIO 测试容量或客户对象存储配额宣传为 Copper 提供的无限空间。

## 8. 失败保护、缺陷修复与成本记录

共发生 5 次恢复 `stage` 失败，全部保持当前站点健康且未覆盖当前数据：

1. 1 次发现 M2-06 新增 `offline-proof.txt` 后，恢复白名单仍停留在旧合同；已补齐可选证明、外内层摘要绑定和旧备份兼容测试。
2. 4 次为同一旁路 Backend 启动问题的诊断复现；根因是恢复目录漏建 `backend/runtime`，生产配置校验正确拒绝不可写的 `COPPER_STORAGE_CAPACITY_FILE` 父目录。已补建目录并新增合同测试。
3. 原清理流程过快，失败后只看到 `unhealthy`。现会在清理前保留 root-only Compose 状态和三服务日志，私钥、密码、环境展开和解密数据仍立即销毁。

业务闭环脚本另有 2 次输入被正常校验拒绝：旧商品的入库包装单位不应伪造为 `kg`，附件只允许 JPG/PNG/WebP。修正为基础数量口径和 PNG 后通过；这两次没有形成库存或资金脏数据。

本轮 x86_64 实机操作窗口约 1 小时 50 分钟，1 名操作员使用发布命令和验收脚本完成；没有手工写 SQL。成功恢复 35 秒，一致性备份 16 秒，恢复峰值约 243 MiB。首次完整验收包含缺陷定位成本，不能直接作为每次客户升级工时；后续同版本正常发布只需发布物校验、备份、迁移/健康、关键业务抽检和回滚点确认。
