# Copper M3 版本、发布节奏与兼容性决策

> 状态：M3-01 生效决策
>
> 冻结来源基线：`v0.1.0-m2-rc.2`
>
> 跟踪 Issue：<https://github.com/soyia/copper_deploy/issues/17>

## 1. 决策摘要

1. Copper 对客户只有一个产品版本。`copper_deploy` 的发布清单定义该版本对应的 Web、Backend、MySQL、部署工具、数据库结构和数据格式组合。
2. M3 起新产品版本使用 `MAJOR.MINOR.PATCH`，候选版只允许 `MAJOR.MINOR.PATCH-rc.N`。内部 M1/M2/M3 里程碑不再写入新版本号。
3. 历史 `0.1.0-m1-rc.*`、`0.1.0-m2-rc.*` 标签、Release、清单和镜像保持原样，不改名、不覆盖、不移动；它们是已发生的验收历史。
4. 首个采用新规则的候选版本 `0.2.0-rc.1` 已作为不可变 M3 验收历史创建。rc.7 的 2026-10-16 修复、源码冻结和真实数据库验证范围以 [本次范围决定](RELEASE_SCOPE_20261016.md) 为准。rc.8 的安全扫描失败和 rc.9 的真实构建/冻结记录均保留。rc.9 镜像发现删除 RPM 后的未归属 Python 缓存残留，下一个候选为 `0.4.0-rc.10`，按 [本轮清理与收口范围](RC10_RELEASE_CLOSURE.md) 重新构建、冻结、扫描及验收。历史候选与门槛记录保持原样。
5. `1.0.0` 只在 M7 正式发布门槛通过后创建，不能因为 M3 技术实现完成就提前使用。
6. 客户自行决定是否以及何时升级。停止维护、无法联网或跳过某次升级，不得让现有已部署版本停止核心业务。

机器可读的固定值位于 `config/release-policy.env`。文档与该文件不一致时，发布必须停止并先通过架构评审消除冲突。

## 2. 六种版本口径

| 口径 | 权威来源 | 用途 | 是否对客户显示为产品版本 |
| --- | --- | --- | --- |
| Copper 产品版本 | `copper_deploy/releases/<version>/components.env` 与同名 Git 标签 | 定义可安装、可升级、可支持的完整组合 | 是，唯一口径 |
| Web/Backend 构建身份 | 镜像摘要、源码提交、真实工作流 Run 或摘要绑定本地构建证据、OCI 元数据 | 追溯组件二进制来源 | 否 |
| 工程包版本 | Web `package.json`、Backend `pom.xml` | Node/Maven 构建和依赖管理 | 否 |
| 数据库结构版本 | `flyway_schema_history` 与不可变 `V<n>__*.sql` | 决定数据库能否被当前 Backend 安全读取和迁移 | 否 |
| 整站备份格式 | 当前为 `copper-backup/v1` | 决定备份工具能否解密、校验和恢复 | 否 |
| 业务导出格式 | 当前为 `copper-export/v1` | 决定 CSV、字典、附件和清单的读取合同 | 否 |

产品版本是组件组合版本，不要求所有组件为了“凑同号”重复构建。组件没有变化时允许复用已验收的不可变镜像摘要，但新发布清单必须继续记录其原始源码提交和真实构建来源。页面、API、日志和交接单对客户展示产品版本，不展示工程包版本冒充整机版本。

## 3. 产品版本语义

### 3.1 语法

- 稳定版：`MAJOR.MINOR.PATCH`，各段为不带前导零的非负整数。
- 候选版：`MAJOR.MINOR.PATCH-rc.N`，`N` 从 1 开始递增。
- 禁止在新版本中使用 `m1`、`m2`、`m3`、日期、分支名、`SNAPSHOT`、`latest` 或任意可移动标识。
- Git 标签固定为 `v<产品版本>`；同一版本、标签和 Release 不得覆盖重发。

### 3.2 变更级别

| 变化 | 版本动作 | 数据库与兼容性要求 | 最低验证 |
| --- | --- | --- | --- |
| 文档、部署脚本或向后兼容缺陷修复 | PATCH | 不改变既有业务语义；如含迁移只能是安全、可验证的修复迁移 | 按风险 L1-L3 |
| 新业务能力、可选配置、向后兼容 API 或结构扩展 | MINOR | 必须提供旧数据迁移、默认行为和回退说明 | L2；含数据则 L3 |
| 删除/重解释已发布业务语义、破坏性 API/数据格式变化 | MAJOR | 必须有正式迁移路径、至少一个稳定周期的弃用说明和完整恢复演练 | L4 |
| RC 内修正 | 递增 `rc.N` | 每个 RC 都是新且不可变的候选发布 | 与实际风险一致 |

在 `1.0.0` 前，MINOR 变化仍不得静默破坏库存、应收应付、资金、审计或客户导出。所谓“0.x 可以随意不兼容”不适用于客户经营数据。

## 4. 发布渠道与节奏

### RC 候选版

- 用于内部验收或明确同意的试点，不作为客户生产自动升级目标。
- 可以按缺陷收敛需要发布，但每个 RC 都必须来自已合入 GitHub `main` 的提交，并有不可变清单、标签、校验值和验证记录。
- RC 之间不承诺任意直接升级；允许来源必须由目标 RC 清单逐项列出并经过实测。

### 稳定版

- 计划性稳定版默认间隔不少于 28 天，避免小微客户频繁停机和团队产生不可持续的交付成本。
- 高风险安全漏洞、库存/往来/资金数据正确性缺陷可以发布紧急 PATCH，不受 28 天限制，但仍不得绕过备份、迁移和健康门槛。
- 稳定版必须至少验证从紧邻的上一稳定版本直接升级；不能验证时不得标记稳定版，必须明确保持 RC 或阻塞。

### 客户控制

- Copper 不主动强制客户升级，不使用远程许可证或心跳禁用旧版本。
- 是否提供某旧版本的人工维护服务由服务合同决定，但停止购买服务不改变客户对现有软件、源码和数据的控制。
- 安全修复需要升级时应明确风险和推荐期限，不能在未获授权时直接操作客户生产环境。

## 5. 兼容性合同

每个采用新规则的发布清单必须明确列出已经实测的 `directUpgradeFrom` 来源。版本大小关系本身不等于兼容；未列出即不支持直接升级。

| 场景 | 规则 |
| --- | --- |
| 同一产品版本恢复 | 继续遵守 M2 `copper-backup/v1` 的完整清单和摘要校验 |
| 旧版本升级到新版本 | 目标清单必须列出来源版本、来源/目标 Flyway 版本、升级模式、停机等级和回退模式 |
| 跳过多个 MINOR | 逐级升级；只有每个被跳过来源都被目标清单明确列出并完成独立实测时才允许直升 |
| 新版本备份交给旧代码 | 默认禁止；除非旧工具明确声明支持该备份格式和目标 schema |
| 人可读业务导出 | 保持可独立读取；它不是可直接导回数据库的升级包 |
| 任意降级 | 禁止根据版本号猜测可行；必须有目标发布的明确回退合同 |

数据库迁移一旦执行，不允许只把 Web/Backend 镜像切回旧版本继续写入。无 schema 变化且清单声明 `image-only` 回退时，可以恢复上一组镜像；存在 schema 或数据变化时，只能切回保留的旁路旧站，或使用升级前已经验证可读的整站备份恢复。禁止为追求“自动回滚”编写未经业务验证的逆向 SQL。

## 6. 新规则发布清单与升级矩阵

最终 `copper-release-<version>.env` 的格式固定为 `copper-release/v1`，必填字段名清单位于 `config/release-manifest-v1.fields`。后续实现可以追加字段，不能删除、改名或重复已有必填字段。

- 产品：版本、渠道（`rc`/`stable`）、发布时间、Deploy 标签和提交。
- 组件：Web/Backend/MySQL 的不可变摘要、源码提交、真实构建来源、平台；本地构建格式见 [本地构建来源](LOCAL_BUILD_PROVENANCE.md)。
- 环境：支持的操作系统、架构、资源下限和容器运行时范围。
- 数据：当前 Flyway 版本、迁移集合 SHA-256、备份格式和导出格式。
- 升级：逐项列出的直接来源版本、来源 schema、升级模式、预计停机等级、最低剩余空间。
- 回退：`image-only`、`retained-sidecar` 或 `verified-backup`，以及允许选择该模式的前提。
- 质量：L1-L4 验证级别、发布说明 SHA-256、已知问题和真实验收记录。

全新安装专用 RC 可以在矩阵中显式追加 `freshInstallOnly: true` 并使用空 `sources`；该模式不允许任何来源升级。此字段只允许布尔真且来源为空，稳定版仍必须列出已实测来源；历史未带该字段的矩阵继续要求非空来源。CLI 生成时 `--fresh-install-only` 与 `--source` 互斥，不能用空数组暗示兼容。

兼容来源不直接塞成难以扩展的环境变量列表。发布清单必须用 `COPPER_UPGRADE_MATRIX_FILE` 和 `COPPER_UPGRADE_MATRIX_SHA256` 绑定一个 `copper-upgrade-matrix/v1` JSON 文件。最小结构为：

```json
{
  "format": "copper-upgrade-matrix/v1",
  "targetVersion": "0.2.0-rc.1",
  "targetSchema": "4",
  "sources": [
    {
      "version": "0.1.0-m2-rc.2",
      "schema": "3",
      "mode": "retained-sidecar",
      "downtimeClass": "maintenance-window",
      "rollbackMode": "retained-sidecar-or-verified-backup"
    }
  ]
}
```

每个 `sources` 条目必须由对应真实演练产生，不能根据 SemVer 自动生成。全新安装不属于升级来源，单独通过空库/空服务器安装验收。清单和矩阵不得使用版本范围模糊代替已测来源，不得使用可移动镜像标签，不得包含密码、私钥、令牌、客户域名或客户数据。

## 7. 三仓责任

| 仓库 | 责任 |
| --- | --- |
| `copper_web` | 生产构建、组件身份、前端兼容说明和受影响页面验证；不定义整机产品版本 |
| `copper_backend` | 生产构建、API/业务兼容、Flyway 追加迁移和数据勾稽；不单独宣布整机可升级 |
| `copper_deploy` | 产品版本、组件清单、升级来源矩阵、发布包、校验值、升级编排、回退和最终验收 |

所有开发分支完成后都必须评审合入 GitHub `main`，本地 `main` 仅快进同步到 `origin/main`。正式版本只能从已合并的 Deploy `main` 提交打标签；Gitee 不参与当前权威发布链。

## 8. M3-01 冻结时的退出与后续边界

M3-01 只冻结版本和兼容性合同，并通过静态契约阻止规则漂移。它不代表以下能力已经实现：

- `copperctl upgrade`、升级锁、升级状态机或自动切换；
- 新的业务数据库迁移或跨版本数据转换；
- 联网/离线升级包；
- 升级中断、断电、磁盘不足或数据库失败的真实恢复验收。

后续任务必须按顺序实现升级预检与备份、隔离迁移与失败保护、联网/离线发布物、真实结构变化升级演练。只有最终演练通过后，才能创建 `v0.2.0-rc.1`。

M3-05 为解决“正式标签只能在最终演练后创建、最终演练又必须冻结精确字节”的先后约束，允许从已经同步的 GitHub `origin/main` 精确提交生成 `--candidate` 字节冻结包。候选目录必须带 `CANDIDATE-NOT-A-RELEASE.json`，不得对外交付，也不构成 Tag 或 Release。最终验收通过后只能在同一 Deploy 提交创建 `v0.2.0-rc.1`；正式构建的 Deploy 包、发布清单、矩阵、发布说明和 ACME 摘要必须与候选逐项一致，否则标签不得发布并必须重新验收。

M3-02 已按上述顺序实现发布契约生成/校验、只读预检和升级前加密整站备份证据绑定，详见 [M3 升级预检与备份准备](M3_UPGRADE_PREPARATION.md)。M3-03 已实现 PREPARED 一次性消费、隔离 Flyway、迁移合同、镜像/版本配置原子切换和失败回滚，详见 [M3 隔离迁移、失败保护与人工切换](M3_UPGRADE_STATE_MACHINE.md)。`PREPARED` 仍只代表可开始隔离迁移，只有 `SWITCHED` 才代表目标版本已对外运行。

M3-04 在发布清单之上定义 `copper-delivery/v1`，把联网和离线交付统一收口为 root-only `READY` 证据，详见 [M3 联网/离线不可变发布物与升级介质](M3_RELEASE_DELIVERY.md)。`READY` 只证明发布文件和目标镜像已经完整交付，不能代替 M3-02 的预检/备份、M3-03 的隔离迁移或人工切换。

M3-05 使用真实 Backend Flyway V4 新增 `system_upgrade_audit`，把升级 ID、来源/目标版本与 schema、升级前备份 ID、发布清单摘要和人工切换结果写入目标数据库审计，同时以 [M3-05 正式 x86_64 升级与空白恢复验收](M3_FINAL_X86_ACCEPTANCE.md) 约束故障恢复、正常升级、继续业务和空白恢复。上述门槛已于 2026-07-14 全部通过；SSH 签名标签 `v0.2.0-rc.1` 固定指向 Deploy 提交 `fc6da6d3f869b8499b7b67813b06ad6ba5cde192`，正式结果、发布摘要和清理证据见 [M3-05 最终验收报告](M3_FINAL_X86_ACCEPTANCE_REPORT.md)。该 RC 不是稳定版，也不改变 `1.0.0` 只能在 M7 门槛通过后创建的决策。
