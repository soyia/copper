# M4-05 日志、容量、RPO/RTO 与故障处置

## 1. 结论与边界

Copper 的单机私有化基线现在把日志增长限制在明确上限内，并用 `copperctl operations` 把“软件具备什么”“当前机器实际做到什么”“购买了什么人工服务”分开显示。

```bash
sudo copperctl operations status
sudo copperctl operations status --json
sudo copperctl operations checklist database
sudo copperctl operations checklist disk --json
```

`operations status` 检查实际容器日志驱动、Backend 文件日志上限、数据盘余量、最近成功备份、异机目标和完整恢复演练。输出不查询业务表，不读取业务明细，不显示站点 ID、备份文件名、口令、私钥、Webhook 或客户数据。

本项定义的是 M4 工程目标与试运营服务边界，不是已经发布的 SLA。M4-07 要在最终空白 x86_64 环境复验，M7 才能依据真实客户规模、人工成本和合同文本决定是否形成正式商业承诺。

## 2. 日志分类与硬上限

| 日志 | 位置与用途 | 轮转/上限 | 保留与权限 | 安全删除 |
| --- | --- | --- | --- | --- |
| 网关 | Web/Caddy 标准输出；访问与代理错误 | Docker `local`，20 MiB × 5，最多约 100 MiB | Docker root-only；只保留受大小限制的段 | 驱动只删除最旧段 |
| 数据库 | MySQL 标准输出/错误 | Docker `local`，20 MiB × 5；单机基线关闭 binlog、general log、slow log | Docker root-only；大小限制 | 驱动只删除最旧段 |
| 应用控制台 | Backend 启动、健康和错误摘要 | Docker `local`，20 MiB × 5 | Docker root-only；大小限制 | 驱动只删除最旧段 |
| 应用文件 | `/var/lib/copper/logs/copper-backend.log` | 单文件 20 MiB；最多 7 天；总量 200 MiB，先到者生效 | 父目录 `0750`，Backend 运行身份可写 | Logback 只删除最旧滚动段 |
| 审计 | MySQL 安全审计、业务单据、库存/资金/核销流水 | 不是文本日志，不按文件轮转；受数据库容量写保护 | 随客户经营数据生命周期保留，接口 RBAC | 禁止自动删除；不得用普通日志代替 |
| 运维 | 备份、监控、恢复、升级状态与事件 | 每条事件流 5 MiB × 2；systemd 每 30 秒最多接收 200 条服务日志 | 状态目录 `0700`、文件 `0600` | 只轮转最旧事件段；当前状态和唯一取证不得自动删 |

三层容器的日志理论上限约 300 MiB，Backend 文件日志 200 MiB，备份与监控两条常驻事件流合计 20 MiB；因此常驻 Copper 管理日志基线约 520 MiB。恢复/升级目录中的诊断证据只在失败任务范围内存在，属于 root-only 取证数据，完成 `discard` 或观察期后由显式命令删除，系统不得因空间紧张擅自删除唯一回滚或故障证据。

MySQL binlog 在单机基线中关闭，因为当前产品没有基于 binlog 的持续归档和时间点恢复流程。只让 binlog 增长不会降低可承诺的 RPO，反而可能耗尽数据库盘。将来引入复制或 PITR 时，必须作为新的恢复格式、容量预算、密钥、校验和演练能力单独验收，不能只打开开关。

## 3. 容量保护优先级

容量同时比较绝对剩余量和百分比，任一条件命中即升级：

| 等级 | 条件 | 强制动作 |
| --- | --- | --- |
| 预警 | `<20%` 或 `<5 GiB` | 业务继续；定位增长并安排扩容 |
| 严重 | `<10%` 或 `<2 GiB` | 阻止新导出、新备份和大附件；不得开始升级/恢复 |
| 阻断 | `<5%` 或 `<1 GiB` | 后端阻止业务写入；只允许诊断、扩容和安全恢复 |

处理顺序固定为：停止新的大文件任务 → 仅轮转已经超过策略的可再生日志 → 扩容或由显式命令删除已验证且超过保留期的备份/导出 → 复查容量和写入探针。不得自动删除数据库、原始附件、审计、唯一成功备份或唯一回滚数据。恢复写入前必须重新通过数据库、容量和经营不变量检查。

## 4. 可兑现的 RPO/RTO 口径

- RPO 是最多可能丢失多少时间的数据，不是“已经配置定时器”。
- RTO 是从确认故障到恢复约定业务能力，不是脚本耗时。
- “恢复完成”必须包含 MySQL/Backend/Web 健康、可写、可恢复及库存、应收应付、资金、核销、附件和审计不变量复核。
- 首次响应、取得客户授权、等待云厂商/域名/硬盘、开始恢复、技术脚本结束和业务复核完成必须分别记录。

### 4.1 工程基线

- 默认计划：每日一次一致性加密整站备份；固定随机偏移，健康主机上的计划间隔仍为 24 小时。
- 当前恢复点目标：24 小时；最近成功备份超过 24 小时即不再显示“目标已达成”，30 小时进入运维预警，48 小时进入严重违约风险。
- 本机备份只覆盖逻辑损坏且本机存储仍可读取的场景。整机/云盘损失要声称同样 RPO，必须有已验证的 NAS 或 S3 兼容异机目标；`local` 不能冒充异地容灾。
- 技术恢复目标：标准兼容环境、可用加密备份、恢复私钥与基础设施均已就绪后 240 分钟内完成自动恢复和技术验证。这是工程目标，不是商业 SLA。
- 证据：M2 的 MySQL 8.4.10、88 表小型夹具完整恢复耗时 483 秒；M3 的真实结构升级从隔离恢复到切换约 117 秒，独立空白恢复约 62 秒。240 分钟为包含数据量变化、人工授权和业务复核余量的保守工程目标，但不能据此推导任意客户数据量都能在 4 小时内恢复。
- 每 180 天至少执行一次客户规模完整恢复演练；只有离线密钥证明而没有数据库、附件和经营不变量复核，不算完整 RTO 证据。

### 4.2 软件与服务责任

| 场景 | 备份/RPO | 响应 | 恢复/RTO |
| --- | --- | --- | --- |
| 软件自助部署 ¥0 | 客户配置、监控并持有恢复密钥；软件提供 24 小时工程目标能力 | Copper 无响应承诺 | 客户自行恢复；没有商业 RTO |
| 标准云部署 ¥349/环境 | 交付时配置每日备份并做一次恢复验证；验收后由客户持续操作 | 验收后不包含持续值守 | 一次交接演练不是持续 RTO |
| 安心维护 ¥349/年 | 客户负责日常备份；4 次、每次原则上不超过 60 分钟的服务额度可用于检查 | 剩余额度内 2 个工作日响应 | 不承诺 RTO；恢复占用额度，超范围另报价 |
| 代运维 ¥99/月或 ¥995/年 | Copper 监控每日备份；客户必须提供健康服务器、授权和异机目标 | 工作时段告警 4 个工作小时内确认，不是 7×24 | 前提就绪后 8 个工作小时运维目标；恢复人工另行确认范围，不含无限免费救援 |

当前低价只能对应自动监控、月度状态检查和有限工作时段响应，不能同时包含 7×24 值守、零 RPO、即时 RTO、无限恢复人工或第三方费用。M7 若试点证明 4/8 工作小时响应成本无法由 `¥99/月` 覆盖，应收紧响应范围或调整代运维价格，不能通过删除核心业务能力维持低价。

## 5. 六类故障处置

机器可读清单位于 `config/operations-policy.json`；现场以 `copperctl operations checklist <类型>` 查看。

| 故障 | 安全停止 | 恢复门槛 | 首要责任/升级 |
| --- | --- | --- | --- |
| 数据库 | 拒绝写入且不返回假成功 | 三层健康、事务/重复提交和经营不变量通过 | 客户基础设施 → 数据库恢复操作员 |
| 磁盘 | 严重时停大任务，阻断时停业务写入 | 扩容/安全清理后容量、写探针通过 | 客户硬盘/云盘负责人 → Copper 产品异常 |
| 备份 | 不发布半包、不更新成功时间、不删旧成功包 | 新包内外层校验、异机目标和离线持钥证明通过 | 备份目标负责人 → Copper 运维 |
| 证书 | 提前告警，不降级公网 HTTP | 域名、完整链、Cookie、readiness 通过 | 客户域名/DNS → 证书操作员 |
| 时间 | 阻断依赖可信时间的高风险动作 | NTP、偏差和审计顺序复核 | 客户基础设施 |
| 断电 | 不放行未知/半迁移状态 | Flyway、表/外键、库存、财务、附件、审计不变量通过 | 客户基础设施 → Copper 恢复操作员 |

M4-06 已在 Ubuntu 24.04 x86_64 隔离主机完成六类真实故障注入和恢复：数据库断开、磁盘分级与真实 ENOSPC、备份目标只读、过期证书、主机时间前跳 120 秒以及三层容器 `SIGKILL` 等价异常断电。恢复后的经营财务、附件和审计不变量通过，详情见 [M4-06 故障恢复验收报告](M4_FAULT_RECOVERY_ACCEPTANCE_REPORT.md)。该结果仍不等于 M4 完成；完全断网和空白主机退出验收属于 M4-07。

## 6. 第三方与客户责任

- 客户持有服务器、云盘、域名、DNS、证书账户、NAS/S3 账户和备份恢复私钥，并保证授权、续费和容量。
- Copper 软件负责按合同安全失败、生成本地证据、执行受支持的备份恢复和不变量校验。
- 云厂商硬盘损坏、账号冻结、域名欠费、DNS 故障、客户误删、客户关闭监控或拒绝扩容不会自动变成 Copper 的 RPO/RTO 责任。
- 代运维也不得让 Copper 成为客户云账号、域名或备份私钥的唯一控制方。
- 所有超范围恢复、非兼容系统、第三方协调和数据修复必须在操作前明确工时、风险、备份和验收，禁止事后才讨论费用。
