# 发布后的分级验证

产品版本、RC/稳定版节奏、组件组合、直接升级来源和回退边界以 [M3 版本与兼容性决策](M3_VERSIONING_AND_COMPATIBILITY.md) 为准。本文件只决定一次具体发布需要执行多深的验证，不能单独证明两个版本可直接升级。

M1 首次建立发布基线时需要完整证明镜像、数据库、密钥、TLS、持久化和失败恢复。基线稳定后，每次发布不必人工重做全部 M1 验收，而是根据改动风险选择门槛。

| 级别 | 典型改动 | 每次必须检查 |
| --- | --- | --- |
| L1 前端 | 页面、样式、无契约变化的交互 | 静态测试、生产构建、镜像元数据、Web 健康、登录和受影响页面冒烟 |
| L2 后端 | 不含数据库迁移的 API 或业务修复 | 单元测试、生产镜像、Backend readiness、关键 API、错误日志和受影响业务链 |
| L3 数据与安全 | Flyway、认证、Cookie、库存、应收应付、收付款、密钥或 Compose | L1/L2，加停机备份、隔离升级、失败门槛、数据勾稽和恢复演练 |
| L4 基线变更 | MySQL/Java/Node/Docker 大版本、服务器迁移、网络/TLS 拓扑变化 | 重新执行空白服务器安装、重启持久性、错误恢复和完整核心业务链验收 |

固定发布顺序是：预检 → 备份（L3/L4）→ 校验目标清单明确允许当前来源版本 → 交付不可变镜像 → 隔离迁移与验证 → 人工切换 → 冒烟验证 → 记录版本与结果。M1-06 已将日常运维、诊断、首次管理员交付和同版本停机备份/恢复收口为正式 `copperctl` 命令；M3-01 至 M3-03 已完成版本合同、准备门槛、隔离 Flyway、人工切换和失败回滚状态机，目标镜像的在线/离线交付仍由后续 M3 项实现。
