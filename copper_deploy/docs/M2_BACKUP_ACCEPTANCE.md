## 一致性与失败恢复

以下场景均保持三层最终 `running/healthy`，没有生成新成功包，也没有改写 `last-success.json`：

1. 可用空间被注入为 0：在进入维护窗口前拒绝执行。
2. 形似 age recipient 但校验和无效的公钥：在进入维护窗口前拒绝执行。
3. Web/Backend 已停止后注入失败：自动拉起三层并等待健康。
4. 打包后、发布前损坏外层文件：校验失败且不发布。
5. 原子发布过程中只移动了主包、尚未移动校验文件时注入失败：自动清理半成品且不改写成功状态。
6. 维护窗口内向备份进程发送 `SIGTERM`：退出非零、清理临时目录并自动恢复三层。

成功路径还验证了先停止 Web/Backend、等待 InnoDB 活跃事务为 0，再读取结构、精确记录数、关键业务余额、附件引用并导出单事务逻辑快照；服务恢复健康后才继续压缩和 age 加密。

## 调度与保留

- systemd service/timer 通过 `systemd-analyze verify`；固定日历为每日 02:30，并带最多 30 分钟随机延迟和错过补跑。
- 真实执行 `--purpose scheduled` 后，文件名和清单均标记为计划备份。
- 将每日、每周、每月保留数临时全部设为 0 时，系统仍强制保留最新成功包，并删除上一份已校验成功的旧包。
- 伪造或摘要不匹配的 `.sha256` 文件不会被当作成功备份进入自动删除候选。
